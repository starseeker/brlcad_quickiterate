Drawing Stack Modernization — Current State, Gaps, and Next Steps
=================================================================

Purpose
-------
This note is the short handoff for the current drawing-stack state.
It focuses on what is already unified, what is still open, and what
future work should prioritize to reach a clean, tested, fully
functional stack that serves both qged and mged/Archer.

The long-form design rationale remains in `draw_migration_plan.rtf`
at the repository root.  Use that file only when the "why" behind a
settled design choice matters; this note is meant to guide active work.

Executive summary
-----------------
The structural merge is done for database-derived geometry and the
LoD redesign is complete.  One real architectural gap remains, and it
is the focus of the new plan in this note.

What is done:
- DB geometry has a single canonical scene model: the BSG tree rooted
  at `ged_drawable::gd_draw_root`, with `bview::gv_draw_root` and
  `bview::bsg_root` both pointing at it.
- qged's `DbiState` / `BViewState` writes through that tree; there is
  no separate qged draw store.
- libdm renders DB content via a single BSG traversal in
  `dm_draw_objs` → `_bsg_view_traverse_impl`, with a single LoD update
  pass (`bsg_lod_update`) at the top.
- LoD is a first-class `BSG_NODE_LOD` node kind with per-view cursors
  (Phase L plan, complete).  No `s_update_callback` side passes, no
  per-view duplicate adaptive scene_objs.

What is NOT yet done — the open architectural gap:
- View-only objects (axes, lines, labels, polygons, gobjs editing
  wireframes, faceplate-adjacent overlays) still live OUTSIDE the BSG
  tree, in four flat `bu_ptbl` tables behind `bv_view_objs(v, ...)`.
  `dm_draw_objs` runs a *second* iteration over those ptbls after the
  BSG traversal.  Two render contracts coexist on the same view.
- `view independent` is a bview boolean that switches `bv_obj_get` to
  `BV_LOCAL_OBJS`, but there is no first-class "view-private subtree"
  concept in the BSG world.  The independence story works by accident,
  not by design.
- The libged `view` / `view obj` / `view gobjs` command surface is
  sprawling, inconsistent, and partly duplicated.  It is the user-
  facing API for adding and removing view-only objects, and it does
  not reflect any of the BSG cleanup that has happened underneath it.
- Legacy per-view duplicate-subtree APIs (`bv_obj_for_view`,
  `bv_obj_get_vo`, `bv_obj_have_vo`, `bv_clear_view_obj`) remain
  exported and partly used in `dbi_state.cpp` adaptive-toggle paths,
  but no new code should be calling them after Phase L4.

The "View-only object unification" plan (Phases V0–V8) below targets
that gap and is now the next work package after the LoD redesign.

What is done
------------
The following points should be treated as current baseline, not work to
redo:

1. Canonical scene ownership is unified on the BSG tree.
   - `gd_draw_root` is the authoritative drawn-set root.
   - `gv_draw_root` is the active view handle to that tree.
   - `bsg_root` aliases `gv_draw_root`; there is no separate per-frame
     sync tree to rebuild.

2. qged's `BViewState` now writes through the BSG tree.
   - Path hashing, invalidation, cached state, and selection remain in
     `dbi_state`.
   - Actual draw leaves are stored under `gd_draw_root`, not in
     `BV_DB_OBJS` as a parallel draw store.

3. The old gv_objs DB-object fallback is gone.
   - `bsg_scene_root_sync` no longer rebuilds DB geometry from
     `BV_DB_OBJS`.
   - `dm_draw_objs` no longer has a legacy DB-object rendering branch.
   - `bv_view_objs_visit_db()` is the migration path for callers that
     need to inspect DB-derived draw objects.

4. The render contract is already carried by the BSG path.
   - two-pass transparency,
   - geometry default color handling,
   - line-width fallback,
   - transform propagation,
   - frame-generation tracking via `gv_frame_rev` / `s_drawn_rev`,
   - lazy illumination change detection via `gd_illum_sensor` and
     `gd_illum_rev`.

5. Cleanup work that should be considered complete:
   - dbpath-keyed draw mutation APIs are the public libged surface;
   - the old path-string mutation/lookup compatibility layer is gone;
   - per-shape backend state now hangs off `bv_scene_obj::s_backend`;
   - deprecated direct `s_dlist*` storage on `bv_scene_obj` is gone;
   - aggregate subtree bbox caching is in place.

Current architecture and invariants
-----------------------------------
These constraints should guide future changes:

- Keep GED policy in libged, tree mechanics in libbsg, and renderer /
  backend state in libdm.
- Keep `dbi_state` as an optional libged-side front-end.  It is useful
  for qged, but it is not the scene graph.
- Do not reintroduce `display_list`, `gd_headDisplay`, or gv_objs DB
  tables as the authoritative drawn-set model.
- Preserve the existing revision contracts: `gd_draw_rev`,
  `gd_mater_rev`, `gd_illum_rev`, `gv_frame_rev`, `s_drawn_rev`, and
  `s_bbox_cached`.
- Preserve multi-mode semantics: a path may still have multiple draw-mode
  leaves at once.

LoD redesign — completed (Phases L0–L7)
---------------------------------------
The Open-Inventor-style LoD redesign described in earlier revisions of
this note has landed in full.  Summary of the resulting contract:

- LoD is a first-class node kind: `BSG_NODE_LOD` (taxonomy bit reserved
  in `include/bsg/defines.h`).  An adaptive path is realised as
  `BSG_NODE_GROUP -> BSG_NODE_LOD -> { BSG_NODE_SHAPE level_0, ... }`.
- Selection is an ops vtable on the LoD node (`bsg_lod_ops`) with
  `select_level(node, view)`, `activate_level(node, level)`, and
  `is_stale(node, view)`.  Two ops sets ship in tree: pop-buffer mesh
  LoD and CSG `ft_adaptive_plot` wrapping (`ged_lod_install_mesh_ops`,
  `ged_lod_install_csg_ops` in `src/libged/bsg_ged_draw.c`).
- Per-view state on an LoD node is a small `view * -> cursor` map
  (level + view metrics), not a duplicate subtree.
- There is exactly one LoD update site: `bsg_lod_update(root, v)` at
  the top of `dm_draw_objs` in `src/libdm/view.c`.  No
  `BViewState::redraw` side pass, no `s_update_callback` for LoD.
- `BV_MESH_LOD` / `BV_CSG_LOD` leaf flags are deprecated.
  `s_update_callback` is no longer fired by libdm for adaptive update.
- `bv_scene_obj_bound` resolves LoD-managed bounds via the LoD node's
  selected child rather than a leaf-side `BV_MESH_LOD` branch.

The phases (L0 wiring, L1 update impl, L2 dm site, L3 producers,
L4 drop per-view duplicate scene_objs, L5 drop the BViewState side
pass, L6 retire `s_update_callback` + leaf flags, L7 image parity)
are all DONE and validated; see git history and the L-test surface
listed below.

Cleanup also already complete:
- dbpath-keyed draw mutation APIs are the public libged surface;
- the path-string mutation/lookup compatibility layer is gone;
- per-shape backend state hangs off `bv_scene_obj::s_backend`;
- direct `s_dlist*` storage on `bv_scene_obj` is gone;
- aggregate subtree bbox caching is in place;
- `gd_illum_solid` retired; illumination identity reads via
  `bsg_sensor_target((bsg_node *)gdp->gd_illum_sensor)`;
- `new_cmd_forms` is no longer a runtime mode toggle (only used at
  open() to gate `dbi_state` allocation).

What is no longer relevant in this note:
- the "long-term unification plan A–E" milestones — done;
- the "Phase 11 backend contract / Phase 12 backend decision /
  Phase 13 cleanup" framing — Phases 11+13 are done; backend default
  decision stays open as Priority 4 below.


Remaining design gaps
=====================
With the LoD redesign and the BSG merge for DB content done, the
honest assessment of correctness, robustness, cleanliness, and
design integrity comes down to four interrelated gaps.  All four
revolve around per-view objects and the user-facing API for adding
and removing them.

Gap 1 — view-only objects are still outside the BSG tree
--------------------------------------------------------
The Phase E/F unification stopped at DB content.  View-only objects
(axes, lines, labels, polygons, gobjs editing wireframes, snap
indicators, miscellaneous overlays) still live in the four flat
ptbls behind `bv_view_objs(v, type)`:

- `v->vset->i->shared_view_objs`            (BV_VIEW_OBJS, shared)
- `v->vset->i->shared_db_objs`              (BV_DB_OBJS,   shared)
- `v->gv_objs.view_objs`                    (BV_VIEW_OBJS, local)
- `v->gv_objs.db_objs`                      (BV_DB_OBJS,   local)

`bv_obj_get(v, type)` adds to one of these depending on `type` and
`v->independent` (which OR's in BV_LOCAL_OBJS).  No producer of a
view-only object ever attaches it to `gv_draw_root`.

Consequences in the renderer:
- `dm_draw_objs` has TWO render contracts running back-to-back
  (`src/libdm/view.c:1010-1063`):
    (a) `bsg_lod_update` + `_bsg_view_traverse_impl` over the BSG
        tree — handles DB content, runs LoD, runs the two-pass
        transparency split;
    (b) a hand-rolled loop over `bv_view_objs(v, BV_VIEW_OBJS)` and
        `bv_view_objs(v, BV_VIEW_OBJS|BV_LOCAL_OBJS)` that calls
        `_dm_draw_scene_obj_internal` directly with
        `transparency_pass=0`.
  This means transparency, depth-mask, and any future per-frame
  invariants we add to the BSG traversal silently do not apply to
  view-only objects.
- The shared-vs-local rendering order for view-only objects is
  hard-coded in libdm; the user/app cannot reorder it via tree
  placement (which is the point of having a tree).
- Selection / picking helpers like `bv_view_objs_select` only see
  ptbl content; the BSG tree is not consulted for view-only hits.
- `bv_view_objs_visit_db()` was added precisely so callers could
  iterate DB content uniformly across the BSG and ptbl worlds —
  but no equivalent exists for view-only content, so callers that
  want "all visible scene objects" must still mix and match.

Consequences in invariant maintenance:
- Memory-pool ownership for view-only objects is split across
  `bview_objs::free_scene_obj` (per-view local pool) and the bview
  set's shared pool, with subtle rules in `bv_obj_get` /
  `bv_obj_get_vo` / `bv_clear_view_obj`.  Adding a fifth bucket
  (e.g. "view-only but lifetime-tied to a DB path") is impractical;
  the model does not extend.
- Dirty / invalidation tracking has no place to live for view-only
  objects.  `gv_frame_rev` and `s_drawn_rev` ride along on the BSG
  traversal, but the ptbl scan does not consult them.

This is the single largest remaining inconsistency in the drawing
stack.  Until it is closed, claims that "the BSG tree is the
canonical scene" are only true for DB-derived content.

Gap 2 — per-view duplicate-subtree API still exposed
----------------------------------------------------
`bv_obj_for_view`, `bv_obj_get_vo`, `bv_obj_have_vo`, and
`bv_clear_view_obj` (in `src/libbv/util.cpp`) implement the
per-view duplicate-`bv_scene_obj` model that Phase L4 explicitly
moved away from for adaptive geometry.  The functions remain:

- declared in `include/bv/util.h` as part of the public libbv API;
- exported, with no deprecation marker;
- still called in `src/libged/dbi_state.cpp` (lines ~3020–3039) in
  the BViewState adaptive-toggle bookkeeping (clear stale per-view
  duplicates when the user toggles `adaptive_plot_csg` /
  `adaptive_plot_mesh` off).

There are two real per-view-object use cases that remain legitimate:
edit-mode highlights and any future "view N has its own copy of
this overlay" scenario.  Today both of those go through the same
`vobjs` map plus the BV_VIEW_OBJS ptbls, blurring the distinction
between "view-only object" and "per-view variant of a shared
object".  Post-L4, no in-tree consumer needs the `vobjs` map for
correctness; the surviving callers are leftover bookkeeping.

Gap 3 — `independent` view is a mode bit, not a scene structure
---------------------------------------------------------------
`bview::independent` is a boolean.  When set:
- `bv_obj_get` quietly OR's `BV_LOCAL_OBJS` into the requested type;
- `bv_view_objs(v, type)` returns the view's local ptbl instead of
  the bview-set's shared ptbl;
- `view independent <view> 1` (in `src/libged/view/view.c:140-204`)
  walks the *shared* DB-object set and re-runs `draw -V <view>` for
  each entry to seed the view's local ptbl.

What it does NOT do:
- It does not give the view a private subtree under `gd_draw_root`;
- It does not change how `dm_draw_objs` walks the BSG tree (the
  whole shared draw root is still walked);
- It does not give libdm any way to know that this view should
  *only* render its own private content.

The end-state is: the user's mental model ("this view is independent")
is implemented as a soft preference about where new objects go,
rather than as a structural property of the rendered scene.  The
comment block above `_view_cmd_independent` is candid about the
fragility: "any object in the independent list that are not present
in the shared set will remain, since there is no way for the library
to know if the intent is to preserve or remove such objects".

Gap 4 — the `view` / `view obj` / `view gobjs` command surface
--------------------------------------------------------------
The user-facing API for adding and removing view-only objects is
the `view` command in libged.  Its current shape leaks every
implementation detail of Gaps 1–3 directly to the user and is
internally inconsistent.

Concrete problems in `src/libged/view/`:

a) Two parallel dispatch entry points coexist:
   - `ged_view_core` (`view.c:664`): the modern subcommand-table
     dispatcher (`_view_cmds`);
   - `ged_view_func_core` (`view.c:772`): a legacy if/else dispatch
     used when `gedp->dbi_state` is NULL.
   They expose overlapping but not identical subcommand sets, and
   `ged_view_func_core` re-dispatches into modern subcommands by
   `BU_STR_EQUAL` chains — duplicated logic, easy to drift.

b) The "current view" indirection in `view.c` is implemented by
   `gd->gedp->ged_gvp = gd->cv;` save/restore around every per-
   subcommand `ged_*_core` call (15+ call sites).  The
   subcommand cores read the current view from `gedp->ged_gvp`
   rather than receiving it as an argument.  This is a known
   thread-hostile pattern and the source of subtle bugs when a
   subcommand fails partway through.

c) `view obj` (`objs.cpp:_view_cmd_objs`) does the same name lookup
   FOUR times in succession (shared view-only ptbl, local view-only
   ptbl, shared db_objs ptbl with two flavors of nested children,
   local db_objs ptbl with the same).  The same fourfold loop is
   repeated for the listing-with-no-args path.  Every new container
   added to `bv_view_objs` widens this footprint linearly.

d) Subcommand grammar is not consistent:
   - `view obj NAME draw` toggles UP/DOWN (text);
   - `view obj NAME arrow` uses `0`/`1` (and supports `width #` /
     `length #` as in-line modifiers);
   - `view obj NAME color` takes `r/g/b` and an optional `-r`
     recursion flag;
   - `view obj NAME del` removes only objects with `BV_VIEWONLY`
     set; for DB-backed it tells the user to use `erase` (which
     lives in a different command);
   - `view gobjs NAME del` calls `bv_obj_put` directly but always
     errors out because `_view_cmd_gobjs` sets `gd->s = NULL`
     unconditionally before subcommand dispatch (`gobjs.cpp:256`);
   - `view obj NAME update` reads `s->s_update_callback` and fires
     it manually (`objs.cpp:280-287`), which is the very pattern
     Phase L6 was trying to retire.
   - `view obj` and `view gobjs` are separate top-level subcommands
     even though `view gobjs create` produces what is conceptually
     a view-only object (it stores it under `BV_DB_OBJS`,
     compounding the confusion).
   - `view vZ` self-deprecates in its help text but still runs four
     near-identical loops over the four ptbls returning a value
     that's clearly wrong (it sets `vZ = calc_mode` rather than
     `vZ = calc_val` in every branch — `view.c:413,418,429,...`).
   - `view obj info mode` falls through to `_view_cmd_old_obj`
     (`objs.cpp:603`), which uses `bsg_view_obj_foreach_solid` and
     `_ged_build_dpp` — a legacy compat path with no test coverage.

e) View-only constructors are flag-sites rather than typed APIs:
   axes, lines, labels, polygons, and gobjs each call
   `bv_obj_get(v, BV_VIEW_OBJS [| BV_LOCAL_OBJS])` and then OR in
   `BV_VIEWONLY` and a payload-type bit by hand.  The caller is
   responsible for getting the flag arithmetic right; there is no
   `bv_view_obj_create_axes(v, ...)` or similar typed entry point.

The result is that "how do I add a user-supplied marker to view N?"
has at least three different answers depending on whether you are
talking to a script user, a libged plugin author, or a libbv API
consumer, and none of them go through the BSG tree.


Two use cases, evaluated against the current state
--------------------------------------------------

Use case A — per-view objects (vs. shared-across-views tree)
............................................................
"Per-view" today actually means three different things, conflated
in the code:

  1. "View-only" — the object exists for visualisation purposes
     and has no DB backing (axes, polygon overlay).  Today: lives
     in BV_VIEW_OBJS ptbl, not in the BSG tree.

  2. "View-private DB content" — the object IS a DB-backed thing
     but the user wants it drawn only in this view (the
     `view independent` workflow).  Today: realised by setting
     `v->independent = 1` and re-running `draw -V` against the
     shared list.  The view still walks the shared `gd_draw_root`,
     so independence relies on the local ptbl not being inserted
     into the shared subtree.

  3. "Per-view variant" — a single shared object whose
     representation differs by view (active-edit highlight,
     adaptive level).  Today: pre-L4 used `vobjs` map; post-L4
     LoD uses BSG_NODE_LOD cursors; edit highlights still use
     the `vobjs` map and the illumination sensor.

These three should not look the same to the user, and they should
not look the same in the API.  The current code mostly conflates
(1) and (2), and exposes (3) only as side-effects of LoD and
selection state.

Use case B — adding/removing user-supplied view-only data
.........................................................
Today, from a script:

  view [-V <name>] obj <name> axes  X Y Z
  view [-V <name>] obj <name> line  ...
  view [-V <name>] obj <name> polygon ...
  view [-V <name>] obj <name> label ...
  view [-V <name>] gobjs <gpath> create <vname>
  view [-V <name>] obj <name> del          # only if BV_VIEWONLY
  view [-V <name>] gobjs <vname> del       # currently broken — gd->s
                                           #   is unconditionally NULL
  zap [-V <name>] -v                       # nuke all view-only objs

  The "shared vs. local" distinction is a CLI flag (-L) on
  `view obj`, but `view gobjs` has no such option.

From a C API:

  s = bv_obj_get(v, BV_VIEW_OBJS [| BV_LOCAL_OBJS]);
  /* hand-fill s_color, s_vlist, s_type_flags |= BV_VIEWONLY |
     BV_AXES, etc.  Caller owns the BV_* flag arithmetic. */
  bv_obj_put(s);   /* removes from ptbl + recycles */

There is no removal API that takes the view + name pair, no
typed constructors, no equivalent of the dbpath-keyed APIs that
exist for DB content, and no integration with the BSG tree.


View-only object unification — implementation plan
==================================================
The phases below close Gaps 1–4 above.  They are sequenced so that
the tree continues to build, test, and render at every step, and
each phase is independently land-able and revertible.  Each phase
ends with a fully green draw test set (see the test surface block
at the bottom of this note).

Naming convention: `Phase V<n>` (View-only) to distinguish from the
completed Phases A–E (BSG merge), L0–L7 (LoD), and the legacy 0–13
numbering.

Phase V0 — audit and freeze the current contract
------------------------------------------------
Goal: nail down "what is a view-only object?" before changing how
it is stored, so the migration in V1+ has unambiguous semantics.

Mechanical work:
- Inventory every in-tree producer of an object that ends up in
  `BV_VIEW_OBJS` (search for `bv_obj_get(.*, BV_VIEW_OBJS`,
  `flags = BV_VIEW_OBJS`, `BV_VIEWONLY`).
- Classify each one by lifecycle: per-frame transient (snap
  indicator), per-session persistent (axes, polygon), or
  edit-bound (gobjs editing wireframe, illumination highlight).
- Document, in this note, the three "per-view" meanings (view-only,
  view-private DB content, per-view variant) and which producer
  belongs in which bucket.
- Add a deprecation marker (`__attribute__((deprecated))`) to
  `bv_obj_for_view`, `bv_obj_get_vo`, `bv_obj_have_vo`,
  `bv_clear_view_obj` so that any new caller is flagged at
  compile time.  The two surviving call sites in `dbi_state.cpp`
  (Gap 2) get a local `#pragma` suppression with a TODO referring
  to Phase V5.

Tests: no behavioural change.  Build must remain warning-clean
under the deprecation markers.

Phase V0 audit snapshot (2026-05-07)
------------------------------------
The in-tree producers currently creating objects in `BV_VIEW_OBJS`
fall into these lifecycle buckets:

- Per-session persistent:
  - `src/libged/view/axes.c` (`_axes_cmd_create`)
  - `src/libged/view/lines.c` (`_line_cmd_create`)
  - `src/libged/view/labels.c` (`_label_cmd_create`)
  - `src/libged/view/polygons.c` (`_poly_cmd_create`,
    `_poly_cmd_import`)
  - `src/libqtcad/QgPolyFilter.cpp` (`QPolyCreateFilter`)
  - `src/qged/plugins/polygon/QPolyCreate.cpp`
    (`QPolyCreate::do_import_sketch`)
- Per-frame / interaction transient:
  - `src/libqtcad/QgMeasureFilter.cpp` (`QgMeasureFilter`)
  - `src/libbv/vlist.c` (`bv_vlblock_obj`)
- Edit-bound:
  - `src/qged/plugins/edit/ell/QEll.cpp`
    (`QEll::update_obj_wireframe`, `QEll::update_viewobj_name`)

Three "per-view" meanings and current producer placement:
- View-only object (visualization-only, no DB identity): axes, lines,
  labels, polygons, measurement overlays, and vlblock overlays above.
- View-private DB content (DB-backed, drawn only in one view): this is
  still driven by `view independent` and `BV_DB_OBJS|BV_LOCAL_OBJS`;
  no audited `BV_VIEW_OBJS` producer belongs in this bucket.
- Per-view variant of a shared object: `QEll` editing wireframe
  overlays currently use `BV_VIEW_OBJS`; adaptive LoD no longer does,
  and the remaining adaptive-toggle cleanup path is in
  `dbi_state.cpp` (Phase V5).

Phase V1 — add a view-scope concept to the BSG tree  [DONE 2026-05-07]
---------------------------------------------------
Introduce structural support in libbsg so view-only objects can
live in the same tree as DB content.  Design choice: a
`BSG_NODE_VIEW_SCOPE` node kind whose children are skipped during
traversal of any view that does not match its `s_v` slot.

Mechanical work:
- Reserve `BSG_NODE_VIEW_SCOPE` in `include/bsg/defines.h`
  (next free bit, e.g. 0x800000000ULL).  Document layout in the
  taxonomy block.
- Add `bsg_view_scope_create(struct bview *v)` and a small
  predicate `bsg_view_scope_visible(node, v)` in libbsg.
- Extend `_bsg_view_traverse_impl` (libdm/view.c) to skip
  view-scope nodes whose owner is not `v`.  When the owner *is*
  `v` (or NULL = shared), traverse normally.
- The render root keeps a single `BSG_NODE_VIEW_SCOPE(NULL)`
  conceptual sub-area for "shared view-only" content so the
  per-view scope check is uniform; a per-view scope hangs off the
  same root and is gated by `v` identity.

No producers move yet.  Tests: existing draw tests must remain
green (the new node kind has no instances in the wild).

Phase V1 implementation snapshot (2026-05-07)
---------------------------------------------
- `BSG_NODE_VIEW_SCOPE 0x800000000ULL` added to `include/bsg/defines.h`
  (bit 35, immediately above the sensor range).  The payload bit-allocation
  comment updated to document the new bit.
- New `include/bsg/view_scope.h` declares:
    bsg_node *bsg_view_scope_create(struct bview *v);
    int       bsg_view_scope_visible(bsg_node *node, struct bview *v);
    void      bsg_view_scope_destroy(bsg_node *scope);
- New `src/libbsg/view_scope.c` implements the three functions.
  `bsg_view_scope_create` allocates via `bv_obj_create` and sets
  `s_type_flags = BSG_NODE_VIEW_SCOPE` and `s_v = v`.
  `bsg_view_scope_visible` returns 1 when `s_v==NULL` (shared) or
  `s_v==v` (owner), 0 otherwise.
- `src/libdm/view.c` (`_bsg_view_traverse_impl`): new block after the

Phase V6 — `view independent` becomes a structural property
-----------------------------------------------------------
Re-express view independence as a tree placement rather than a
mode bit:

- A view marked independent gets a private `BSG_NODE_VIEW_SCOPE`
  hung off `gd_draw_root` (or a private root entirely, depending
  on whether shared geometry should be hidden — the latter is the
  more honest implementation of "independent").
- `view independent <view> 1` clones (or moves, depending on the
  user's intent — make it an explicit option) shared draw entries
  into the private scope.
- `view independent <view> 0` discards the private scope and lets
  the view fall back to the shared draw root.
- `bview::independent` becomes a derived property (computed from
  whether the view has its own private scope) rather than a
  source of truth.

Tests: existing `view independent` behaviour must be preserved.
Add a `ged_test_view_independent` suite with create / draw /
toggle-back / re-share scenarios.

Phase V7 — libged `view` command consolidation
----------------------------------------------
Refactor `src/libged/view/` to address Gap 4 directly.  This is
the user-visible payoff for the work in V0–V6.

Mechanical work:
- Delete `ged_view_func_core` (the legacy non-`dbi_state` dispatch
  path).  All callers reach `ged_view_core` unconditionally; the
  modern subcommand table is the only API.
- Replace the 15+ `ged_gvp` save/restore patterns in `view.c` with
  a small inline helper, or change subcommand cores to take an
  explicit `struct bview *` instead of reading `ged_gvp`.  The
  latter is the right long-term shape; the former is the safe
  intermediate step.
- Collapse `view obj` and `view gobjs` into a single `view obj`
  command with a `-g <dbpath>` option for the gobjs case.
  `view gobjs` becomes a deprecated alias.
- Rewrite `view obj` lookup / listing as a single BSG walk over
  the view-scope subtree(s).  Drop the fourfold ptbl scan.
- Standardise subcommand grammar:
   - `view obj [-V view] [-L] create  <name> <type> <args...>`
   - `view obj [-V view] [-L] remove  <name>`
   - `view obj [-V view] [-L] list    [<glob>]`
   - `view obj [-V view] [-L] info    <name> [field]`
   - `view obj [-V view] [-L] set     <name> <field> <value>`
  All sub-typed creators (`axes`, `line`, `polygon`, `label`,
  `arrow`) become `<type>` selectors of the unified `create`
  rather than independent subcommands.  Old subcommand names
  remain as deprecated aliases for one release cycle.
- Fix `view gobjs del` so the lookup populates `gd->s` before
  dispatch (the bug at `gobjs.cpp:256`).
- Remove or finish `_view_cmd_old_obj` — it has no test coverage
  and is reachable only via `view obj <p> info mode` on the
  legacy non-`dbi_state` code path.
- Fix the `view vZ` `vZ = calc_mode` bug (the assignment should
  be `vZ = calc_val`).  Decide whether `view vZ` survives at all;
  it self-deprecates in its own help text.

Tests: a new `ged_test_view_command` suite covering grammar
parity, alias behaviour, `-V` semantics, `-L` semantics, and
error reporting.  Existing user scripts (mged, archer) that use
the old subcommand spellings must continue to work — the alias
layer is the contract.

Phase V8 — public C API for view-only objects + deprecation cleanup
-------------------------------------------------------------------
Final-form public API; this is what user code (tools, plugins,
libqtcad, libtclcad) is expected to call after the refactor.

Public surface:
- `bv_view_obj_create(v, name, type, opts)` — generic constructor

Why this sequencing
-------------------
- V0 makes the next steps land safely by giving the deprecation
  guardrails a chance to flag bad new callers immediately.
- V1 + V2 separate "structural support exists" from "behaviour
  changed" — V1 is pure additions, V2 is the contract change with
  no new producers yet.
- V3 is the heavy migration, but every producer is a small, local
  change with image-diff tests right next to it.
- V4 is the cleanup that justifies V1–V3 by deleting the parallel
  ptbl world.
- V5 finishes Gap 2 (per-view duplicate API) once the LoD path
  has confirmed the new model is sufficient.
- V6 fixes Gap 3 (`independent` mode) by reusing the V1
  view-scope mechanism, so it's a small additional step rather
  than a separate redesign.
- V7 is the user-visible cleanup of the `view` command surface.
  It sits late so it can lean on the simplified storage model
  from V1–V6.
- V8 is purely deprecation removal and documentation.

What not to undo
----------------
- Do not make the gv_objs DB ptbls authoritative again.
- Do not move qged's higher-level state model into libbsg.
- Do not add backend-specific fields back onto `bv_scene_obj`.
- Do not reintroduce a second LoD update path; `dm_draw_objs`
  calling `bsg_lod_update` is the single update site.
- Do not push LoD selection logic back into per-leaf callbacks;
  `s_update_callback` for adaptive update is gone for good.
- Do not reintroduce per-view duplicate `bv_scene_obj` subtrees
  for adaptive geometry (Phase L4 contract).
- Do not re-fuse "is this a DB object?" with "is this an LoD
  leaf?" on `bv_scene_obj`.
- Do not add new producers that call `bv_obj_for_view` /
  `bv_obj_get_vo` / `bv_obj_have_vo` / `bv_clear_view_obj`
  (these are deprecation candidates as of V0).
- Do not add new direct callers of `bv_view_objs(v, BV_VIEW_OBJS
  [| BV_LOCAL_OBJS])`; new code goes through the V8 typed API.
- Do not extend the `view` / `view obj` / `view gobjs` command
  surface in its current shape; new functionality is added under
  the V7-consolidated grammar (or, before V7, with explicit
  awareness that the surface is going to be reshaped).
- Do not judge success by qged alone; the target remains one
  stack that works cleanly for qged and for mged/Archer.
