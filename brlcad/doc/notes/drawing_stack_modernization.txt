Drawing Stack Modernization — Concise Status and Next-Session Plan
=================================================================

Purpose
-------
This note is the short handoff for future drawing-stack work.  It records
what is already settled, why that work matters, and what still needs to be
done to finish the migration to one clean rendering model.

Use `draw_migration_plan.rtf` only when deeper historical design rationale is
needed.  This file should stay focused on current status and the remaining
implementation plan.

Executive summary
-----------------
The main architectural merge is done:
- DB-backed drawing now uses the BSG tree as the canonical scene model.
- LoD is a first-class BSG concept, not a per-view duplicate-subtree hack.
- View-only objects also now live on the BSG side, and the `view obj`
  command surface has been consolidated around the unified grammar.
- Public typed view-object APIs exist for creation, lookup, iteration, and
  simple mutations.

Why that matters:
- qged, libged, and libdm now mostly agree on one scene representation.
- Most rendering invariants now live in one traversal path instead of split
  across BSG and ad hoc ptbl walks.
- New work should build on typed view-object APIs and BSG view-scope nodes,
  not on legacy `BV_VIEW_OBJS` storage assumptions.

What still blocks a fully finished stack:
- Tcl/Archer/mged refresh still has a legacy render path outside
  `dm_draw_objs`.
- Some producers/readers still rely on compatibility paths instead of the
  typed API.
- The per-view-variant/highlight model is still unresolved, which blocks the
  final `QEll` migration.
- Final deprecation removal and backend-default policy are intentionally
  deferred until the migration work is complete.


Completed baseline (do not reopen without a new design reason)
--------------------------------------------------------------
1. Canonical drawn scene ownership is unified on the BSG tree.
   - `ged_drawable::gd_draw_root` is authoritative.
   - `bview::gv_draw_root` / `bview::bsg_root` are handles to that tree.
   - qged `dbi_state` is front-end state, not a parallel scene store.

2. LoD redesign is complete.
   - `BSG_NODE_LOD` is the adaptive representation.
   - Per-view LoD state is cursor-based, not duplicate-subtree based.
   - `dm_draw_objs` owns the single LoD update site.

3. View-only object unification Phases V1-V8 are complete.
   - `BSG_NODE_VIEW_SCOPE` exists and drives shared vs per-view visibility.
   - libdm renders from the BSG tree only.
   - `view independent` is structural via a private view scope.
   - `view obj` uses the unified `create/remove/list/info/set` grammar.
   - Public APIs exist: `bv_view_obj_create`, typed wrappers,
     `bv_view_obj_find`, `bv_view_obj_visit`, and typed setters.

4. Typed setter groundwork is complete.
   - `bv_view_obj_set_color`
   - `bv_view_obj_set_line_width`
   - `bv_view_obj_set_visible`

5. Early typed-API adoption work is already in place.
   - libbv readers in `hash.c` and `snap.c` use typed iteration.
   - libged readers in `view.c`, `draw2.cpp`, `rtcheck2.cpp`, and
     `polygons.c` use typed iteration / lookup where the change was
     mechanical.


Still-open work, in priority order
==================================

Priority 1 — retire the Tcl/legacy render path (Phase T)
--------------------------------------------------------
This is the highest-value remaining work.  Until it lands, the project still
has two drawing systems: the BSG pipeline and the Tcl-only legacy path.

Phase T0 is done:
- The remaining legacy callers and adornment producers were audited.
- Deprecation notes were added to `dm_draw_viewobjs` and `bv_data_tclcad`.

The remaining implementation work is:

### T1 — migrate Tcl faceplate adornments onto BSG view-scope objects
Status: NOT STARTED.

Why:
- Today the Tcl adornments in `src/libtclcad/view/{arrows,axes,lines,labels,polygons}.c`
  still write into `gv_tcl` state that bypasses the unified BSG path.
- Until these producers move, Archer and Tcl-driven mged cannot share the
  same rendering contract as qged.

What to do:
- Replace each `gv_tcl.gv_data_<kind>` / `gv_tcl.gv_sdata_<kind>` producer
  with lookup/create of named BSG view-scope objects.
- Update mutable properties through typed setters and add kind-specific
  setters only when truly needed.
- Preserve the visual distinction between normal and selected adornments,
  but do not preserve the duplicated Tcl state structure verbatim.
- Remove the matching `dm_draw_<kind>` helper once no producer depends on it.

Files to start with:
- `src/libtclcad/view/arrows.c`
- `src/libtclcad/view/axes.c`
- `src/libtclcad/view/lines.c`
- `src/libtclcad/view/labels.c`
- `src/libtclcad/view/polygons.c`
- `src/libdm/view.c`
- `include/bv/tcl_data.h`

Validation focus:
- `ged_test_drawing_faceplate`
- image parity for selected vs non-selected adornments
- line-width / pixel-size behavior in view space

### T2 — switch refresh to `dm_draw_objs`
Status: NOT STARTED.

Why:
- Once T1 producers are migrated, the refresh path itself must stop calling
  `dm_draw_viewobjs` so all front ends use the same renderer.

What to do:
- Replace both `dm_draw_viewobjs(...)` calls in
  `src/libtclcad/view/refresh.c` with `dm_draw_objs(...)`.
- Investigate the duplicate call in the default path and decide whether it is
  intentional or dead copy-paste.
- Validate overlay / interlay / underlay handling in `go_refresh_draw`.

### T3 — delete the legacy renderer
Status: NOT STARTED.

Why:
- This is the point where "single drawing system" becomes a true project
  statement rather than an approximation.

What to do:
- Remove `dm_draw_viewobjs` from libdm and its header declarations.
- Remove `bv_data_tclcad` and the `gv_tcl.*` state from `bview`.
- Remove obsolete `dm_draw_*` helpers and the standalone `dm_obj` path in
  `src/libtclcad/dm.c`.

### T4 — add parity coverage for the refresh path
Status: NOT STARTED.

Why:
- T1-T3 change front-end behavior, not just storage.  They need direct tests,
  not only indirect draw-suite coverage.

What to do:
- Extend existing faceplate/front-end tests or add `ged_test_archer_bsg`.
- Drive `to_refresh_view` directly and compare output against
  `dm_draw_objs` for the same scene.


Priority 2 — finish typed-API adoption (Phase A)
------------------------------------------------
The architecture is in place, but not every producer/reader uses it directly
yet.  The remaining work should eliminate compatibility-path dependence.

### A0 — finish libbv internal producer migration
Status: PARTIAL.

Already done:
- Reader migrations in `src/libbv/hash.c`
- Reader migrations in `src/libbv/snap.c`

Still to do:
- Migrate `src/libbv/vlist.c::bv_vlblock_obj`
- Migrate `src/libbv/polygon.c::bv_create_polygon`
- Verify that neither producer still depends on legacy ptbl insertion side
  effects from `bv_obj_get`

### A1 — finish libged producer migration
Status: PARTIAL.

Already done:
- typed reader/lookup conversions in `view.c`, `draw2.cpp`, `rtcheck2.cpp`,
  and `view/polygons.c`

Still to do:
- Move polygon producers in `src/libged/view/polygons.c` together with the
  libbv/qged polygon-side migration so all polygon creation paths land on the
  same final API shape.

### A2 — migrate libqtcad and qged plugin producers
Status: NOT STARTED.

Why:
- These are the remaining user-facing producers outside the completed V work.

Targets:
- `src/libqtcad/QgMeasureFilter.cpp`
- `src/libqtcad/QgPolyFilter.cpp`
- `src/qged/plugins/polygon/QPolyCreate.cpp`
- `src/qged/plugins/polygon/QPolyMod.cpp`
- `src/qged/plugins/edit/ell/QEll.cpp`

Important constraint:
- `QEll.cpp` is blocked by Phase H below.  Do not force that migration onto
  the generic view-only model until the per-view-variant/highlight design is
  settled.


Priority 3 — define the per-view-variant / highlight model (Phase H)
--------------------------------------------------------------------
Status: NOT STARTED.

Why:
- The remaining edit/highlight use case is not the same as ordinary
  view-only objects.
- `QEll` and future edit tools need a sanctioned API instead of reaching into
  sensor or legacy compatibility paths.

What to decide:
- Whether per-view variants should be a dedicated node concept or an overlay
  scope attached to the edited object.
- What the public `bv_scene_obj_highlight_*` API should look like on top of
  `gd_illum_sensor`.

Deliverables:
- a clear design choice
- public highlight API
- `QEll` migration onto that API


Priority 4 — final cleanup after the migrations are stable (Phase D)
--------------------------------------------------------------------
Status: NOT STARTED.

Run this only after T and A are complete and the tree has been stable for at
least one release cycle.

Cleanup targets:
- remove `bv_view_objs(...)` and the cache fields that exist only for
  compatibility
- remove the `BV_VIEW_OBJS` auto-routing fallback from `bv_obj_get`
- remove remaining deprecated flag bits / compatibility shims
- remove the legacy `bview::independent` boolean if no live readers remain


Priority 5 — backend default decision (Phase B)
-----------------------------------------------
Status: NOT STARTED.

This is an open policy choice, not a migration blocker.

What to do:
- add a benchmark-style draw test for `dm-qtgl` vs `dm-swrast`
- codify the default backend in qged and the matching mged path
- document the rationale once data exists


Suggested next-session order
----------------------------
1. Finish Phase T1 for one Tcl adornment kind end-to-end and validate image
   parity.
2. Repeat T1 for the remaining adornment kinds.
3. Land T2 and confirm refresh-path parity.
4. Land T3/T4 once the old path has no remaining producers.
5. Finish polygon/vlist typed-API migration work in A0/A1/A2.
6. Resolve Phase H and then migrate `QEll`.
7. Run Phase D cleanup only after the compatibility window is no longer needed.


Do not re-open
--------------
- BSG ownership of DB-backed draw content
- LoD node architecture
- V1-V8 view-only object unification
- unified `view obj` command grammar
- typed setter API foundation
