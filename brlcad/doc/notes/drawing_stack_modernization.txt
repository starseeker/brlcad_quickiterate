Drawing Stack Modernization — Current State, Gaps, and Next Steps
=================================================================

Purpose
-------
This note is the short handoff for the current drawing-stack state.
It focuses on what is already unified, what is still open, and what
future work should prioritize to reach a clean, tested, fully
functional stack that serves both qged and mged/Archer.

The long-form design rationale remains in `draw_migration_plan.rtf`
at the repository root.  Use that file only when the "why" behind a
settled design choice matters; this note is meant to guide active work.

Executive summary
-----------------
The structural merge is mostly done.

There is now one canonical drawn-set model for GED consumers:
- the drawn database scene lives in a BSG tree rooted at
  `ged_drawable::gd_draw_root`;
- views point at that tree through `bview::gv_draw_root`;
- `bsg_root` is now just an alias for `gv_draw_root`;
- qged's `DbiState` / `BViewState` no longer maintain a separate draw
  store and instead write through the same BSG tree used by MGED/Archer;
- libdm renders through the BSG traversal path rather than a legacy
  display-list-owned model.

That means the qged/ged drawing test stack and the newer BSG stack are
no longer separate architectures.  qged still has an extra front-end
state layer (`dbi_state`) for path bookkeeping, invalidation, and
selection, but it now targets the same underlying scene tree and render
contract as mged/Archer.

What is done
------------
The following points should be treated as current baseline, not work to
redo:

1. Canonical scene ownership is unified on the BSG tree.
   - `gd_draw_root` is the authoritative drawn-set root.
   - `gv_draw_root` is the active view handle to that tree.
   - `bsg_root` aliases `gv_draw_root`; there is no separate per-frame
     sync tree to rebuild.

2. qged's `BViewState` now writes through the BSG tree.
   - Path hashing, invalidation, cached state, and selection remain in
     `dbi_state`.
   - Actual draw leaves are stored under `gd_draw_root`, not in
     `BV_DB_OBJS` as a parallel draw store.

3. The old gv_objs DB-object fallback is gone.
   - `bsg_scene_root_sync` no longer rebuilds DB geometry from
     `BV_DB_OBJS`.
   - `dm_draw_objs` no longer has a legacy DB-object rendering branch.
   - `bv_view_objs_visit_db()` is the migration path for callers that
     need to inspect DB-derived draw objects.

4. The render contract is already carried by the BSG path.
   - two-pass transparency,
   - geometry default color handling,
   - line-width fallback,
   - transform propagation,
   - frame-generation tracking via `gv_frame_rev` / `s_drawn_rev`,
   - lazy illumination change detection via `gd_illum_sensor` and
     `gd_illum_rev`.

5. Cleanup work that should be considered complete:
   - dbpath-keyed draw mutation APIs are the public libged surface;
   - the old path-string mutation/lookup compatibility layer is gone;
   - per-shape backend state now hangs off `bv_scene_obj::s_backend`;
   - deprecated direct `s_dlist*` storage on `bv_scene_obj` is gone;
   - aggregate subtree bbox caching is in place.

Current architecture and invariants
-----------------------------------
These constraints should guide future changes:

- Keep GED policy in libged, tree mechanics in libbsg, and renderer /
  backend state in libdm.
- Keep `dbi_state` as an optional libged-side front-end.  It is useful
  for qged, but it is not the scene graph.
- Do not reintroduce `display_list`, `gd_headDisplay`, or gv_objs DB
  tables as the authoritative drawn-set model.
- Preserve the existing revision contracts: `gd_draw_rev`,
  `gd_mater_rev`, `gd_illum_rev`, `gv_frame_rev`, `s_drawn_rev`, and
  `s_bbox_cached`.
- Preserve multi-mode semantics: a path may still have multiple draw-mode
  leaves at once.

Assessment of the qged/ged + BSG merge
--------------------------------------
The merge is functionally advanced and architecturally sound.

What is working:
- qged's path/state layer is no longer fighting the BSG tree.
- MGED/Archer and qged now converge on one renderable scene structure.
- DB-object iteration helpers have been updated for the BSG-backed world.
- Core drawing regressions (basic, faceplate, BSG stability/parity,
  view-object tests) have dedicated coverage.

What is still not fully finished:
- adaptive/view-specific drawing behavior is not yet fully expressed as a
  clean BSG-native contract; the next section ("LoD: design rethink")
  is the design and plan for closing this gap;
- some redraw/update responsibilities still live in `BViewState::redraw`
  as explicit side passes rather than in a shared scene-graph traversal
  — this is a direct consequence of the above;
- remaining image-level gaps are concentrated in LoD, hidden-line, and
  shaded-mode interactions rather than in basic draw/erase ownership.

In short: the stacks are merged for core scene ownership and rendering,
but not yet fully merged for all adaptive per-view behaviors.

LoD: design rethink
===================
LoD is the largest remaining architectural gap, and the place where the
"push everything into the scene object" model from the original qged
work hurts the most.  This section is a deliberate redesign, not a
patch-list against the current code.

What exists today
-----------------
- mesh LoD (pop-buffer) in libbv: levels precomputed and cached, level
  selection driven by view scale and screen-space bbox metrics, with
  per-level memshrink to keep RAM cost bounded;
- adaptive CSG wireframe plotting in libged: `ft_adaptive_plot` in each
  primitive's idb_meth, view-frustum-clipped via OBB, regenerates vlists
  when curve_scale, point_scale, or view_scale change beyond a threshold;
- `view lod` user command for visibility settings and tunables;
- LoD data caching with cross-run validation (`ged_test_lod_crossrun`);
- per-view "view objects" parallel to the parent scene object, kept in
  `bv_scene_obj::i->vobjs` and selected at draw time by
  `bv_obj_for_view()`;
- libdm honoring `s_update_callback` during the draw walk
  (libdm/view.c calls it on every drawable just before backend draw);
- `BViewState::redraw()` running its own LoD update pass over `s_map`
  so zoom/redraw_on_zoom-driven view changes propagate even when the
  in-draw callback path is bypassed (qged-only side loop);
- the public BSG LoD API (`bsg_lod_update`, `bsg_lod_stale`) is still a
  Phase-4 stub — it walks the root's immediate children only, calls
  `bv_mesh_lod_view` for `BV_MESH_LOD` flagged leaves, and conservatively
  reports "not stale".

Why the current shape is hard to reason about
---------------------------------------------
The original qged drawing work pushed responsibility for "how should
this object be drawn in this view" down into the scene object itself.
Two kinds of state then ended up living on `bv_scene_obj`:

  1. identity / classification:
       - DB object vs. view-only object (BV_DB_OBJS vs. BV_VIEW_OBJS),
       - "is this leaf an LoD leaf?" (BV_MESH_LOD / BV_CSG_LOD flag bits
         on `s_type_flags`),
       - per-view duplicates in `i->vobjs` so each view can have its
         own active level / vlist.

  2. update mechanism:
       - `s_update_callback` fired by the renderer during draw,
       - explicit re-walks from `BViewState::redraw()` to compensate
         when no draw happened but state still needed to advance.

The clunky parts are the predictable consequence of that:
  - "what does this leaf actually represent" is answered by combining
    a flag bit, a callback pointer, an i->vobjs entry, and possibly an
    s_path — different combinations for mesh LoD, CSG LoD, view-only
    overlays, edit highlights, and faceplate widgets;
  - the *renderer* ends up with policy responsibilities (it has to
    decide when to call the update callback, with what view, before
    which draw);
  - the *front end* (qged) ends up with a parallel update responsibility
    because the renderer's callback path doesn't always fire (e.g.
    redraw-on-zoom from BViewState, multi-view Quad layouts, headless
    image generation);
  - per-view duplicate scene objects cost memory and duplicate
    invalidation paths (`bv_clear_view_obj`, `bv_obj_have_vo`,
    `bv_obj_for_view`) for what is conceptually "show level N for
    this view" rather than "store an entire alternate object per view";
  - bbox computation has to special-case BV_MESH_LOD because the bbox
    actually lives in the LoD container hanging off `draw_data`, not
    in any view-shared place.

What Open Inventor / Coin3D / Obol get right
--------------------------------------------
Open Inventor's LoD design is worth borrowing because it cleanly
separates the three jobs we have currently fused:

  - *selection*:
      `SoLOD` / `SoLevelOfDetail` are grouping nodes whose *only* job
      is to choose, at traversal time, which child to render based on
      the current action's view state (camera distance for SoLOD,
      projected screen-space bbox area for SoLevelOfDetail).
  - *representation*:
      the children of an LoD group are ordinary scene-graph subtrees,
      one per detail level.  They are not "LoD nodes" — they are just
      geometry.  The geometry has no idea it is being switched between.
  - *triggering*:
      level selection happens during traversal of a render action, not
      via callbacks fired from the backend.  The traversal is the same
      walk that produces the frame; the action carries the view, the
      LoD node consults it, the representation children draw.  No
      out-of-band "redraw side loop" is needed because nothing about
      LoD lives outside the traversal.

Two consequences of that design that we want:
  - the scene graph is *shared* across views.  Per-view state is the
    cursor that identifies which child the LoD group should pick,
    plus a small cache of "what view scale did I last pick at" for
    staleness detection.  It is not a duplicate subtree per view.
  - geometry leaves do not carry "I am an LoD-aware leaf" flags.
    Aware-ness lives in the parent grouping node.

Best-answer design for BRL-CAD
------------------------------
Promote LoD from "a flag bit on a drawable leaf plus a callback the
renderer fires" to "a first-class BSG node kind that owns selection".
The taxonomy slot is already reserved (`BSG_NODE_LOD`,
include/bsg/defines.h:61) but no producer creates such nodes today.

Concretely:

  1. LoD becomes a tree node, not a leaf attribute.
     - A path that wants adaptive drawing is realized as
         BSG_NODE_GROUP (path/mode group)
           └─ BSG_NODE_LOD          (LoD selector)
                ├─ BSG_NODE_SHAPE   (level 0 representation)
                ├─ BSG_NODE_SHAPE   (level 1 representation)
                └─ ...              (levels added lazily)
     - For pop-buffer mesh LoD, the children are the same `bv_scene_obj`
       leaves the libbv pop-buffer code already produces; the LoD node
       owns the pool, not a single leaf.
     - For CSG wireframe LoD, the children are vlist-bearing leaves
       regenerated by `ft_adaptive_plot`; the LoD node owns the
       regeneration policy, not a single leaf.
     - Static (non-adaptive) drawing has no LoD node at all — the path
       group's child is just a SHAPE leaf, exactly as today.

  2. Selection is a small ops vtable on the LoD node.
     - `bsg_lod_ops::select_level(node, view) -> int` decides the level
       index from view state (gv_scale, gv_perspective, screen-space
       bbox area, curve_scale, point_scale).
     - `bsg_lod_ops::activate_level(node, level)` makes that level the
       node's currently-rendered child for the calling view (cheap:
       set a per-view cursor; expensive only the first time, when the
       child does not yet exist and must be materialised).
     - `bsg_lod_ops::is_stale(node, view) -> bool` compares cached
       view metrics against current ones for that view.
     - Two concrete ops sets ship in the tree: one wrapping libbv
       pop-buffer mesh LoD, one wrapping libged CSG `ft_adaptive_plot`.

  3. Per-view state is a cursor, not a duplicate subtree.
     - The LoD node carries a small `view * -> {level, view_scale,
       curve_scale, point_scale, perspective_flag, last_seen_frame_rev}`
       map.  That replaces `bv_scene_obj::i->vobjs` for the LoD case.
     - Children (the level representations) are shared across views.
     - `bv_obj_for_view()` is preserved for legitimately per-view
       objects (edit-mode highlights, faceplate widgets, view-only
       overlays).  It is no longer the LoD path.

  4. There is exactly one place LoD updates run: the render walk.
     - `dm_draw_objs(dmp, v)` calls `bsg_lod_update(v->gv_draw_root, v)`
       once at the top.  That walk visits every BSG_NODE_LOD node, asks
       `is_stale`, and if so calls `select_level` then `activate_level`.
     - The subsequent traversal in libdm draws whatever child the LoD
       node has currently selected for `v`.  The renderer never calls
       back into update logic.
     - `s_update_callback` is removed from the per-leaf drawable path.
       Adaptive regeneration triggered by the LoD ops is the only
       update mechanism.

  5. Identity ("DB object" vs. "view object") moves out of the leaf.
     - DB-ness is expressed by tree placement: the path group above the
       LoD node (or above a static SHAPE leaf) is what carries the
       db_full_path.  The leaf does not need BV_DB_OBJS to be drawable.
     - View-only overlays remain leaves under view-scoped roots and
       have no LoD parent.
     - This finishes the BV_DB_OBJS / BV_VIEW_OBJS collapse already
       under way (see Phase B/E in the long-form plan).

  6. Mechanism in libbsg, policy in libbv/libged.
     - libbsg owns: the LoD node kind, the per-view cursor map, the
       traversal hook, the bbox aggregation, child lifecycle.
     - libbv owns: pop-buffer level computation, mesh memshrink,
       cache key plumbing, screen-space metric helpers.
     - libged owns: `ft_adaptive_plot` driver, OBB-vs-frustum cull,
       curve_scale/point_scale wiring from `gv_s`.
     - The ops vtables are how libbsg pulls policy in without depending
       on libbv/libged headers.

Why this is the right shape
---------------------------
- It makes the answer to "where does LoD update happen?" exactly one
  line: `dm_draw_objs` calls `bsg_lod_update(root, v)` before drawing.
  No qged-side compensation, no renderer callbacks, no parallel paths.
- It eliminates the per-view duplicate scene_obj for adaptive cases.
  Memory and invalidation cost scale with paths, not paths × views.
- It localises the awkward special-cases (BV_MESH_LOD bbox math,
  adaptive_plot regeneration) to the ops implementation, instead of
  letting them leak into bv_scene_obj_bound, dm_draw_scene_obj, and
  BViewState::redraw simultaneously.
- It plays well with non-Qt front ends: mged/Archer hit the same
  `dm_draw_objs` path qged hits, so adaptive zoom works identically
  without anyone having to remember to run a side loop.
- It keeps both existing strengths intact: the pop-buffer mesh LoD's
  pre-cached, memshrinkable level set is exactly the right thing to
  hang under an LoD node, and the CSG wireframe regen-on-view-change
  is exactly an `is_stale` + `activate_level` cycle.
- It maps directly onto BSG_NODE_LOD, which is already reserved in the
  taxonomy.  Nothing in this design requires inventing new core
  concepts; it requires populating a slot the tree already has.

Implementable multi-step plan
-----------------------------
The phases below are intentionally sequenced so the tree continues to
build, test, and render at every step.  Each phase ends with a fully
green draw test set.

Phase L0 — define the LoD node abstraction in libbsg  DONE
  - Added `bsg/lod_ops.h`: `bsg_lod_ops` vtable, `bsg_lod_view_cursor`,
    `bsg_lod_payload`, and constructor API declarations.
  - `src/libbsg/lod_node.c`: `bsg_lod_node_create`, `bsg_lod_node_set_ops`,
    `bsg_lod_node_attach_level`, `bsg_lod_node_get_cursor`,
    `bsg_lod_node_active_level`, `bsg_lod_node_level_count`.
  - `_bsg_view_traverse_impl` in libdm/view.c handles BSG_NODE_LOD by
    reading the per-view cursor and recursing into the selected child only.
  - libbsg unit test `test_lod_node.c` (libbsg_lod_node) — 11 tests PASS.
  - `ged_test_bsg_view_obj` section [17] — synthetic ops lifecycle test
    (176/176 checks PASS).

Phase L1 — implement `bsg_lod_update` and `bsg_lod_stale` for real  DONE
  - Replaced Phase-4 stub in `src/libbsg/lod.cpp` with a recursive DFS
    that, at each BSG_NODE_LOD node, calls `ops->is_stale` and on true
    calls `ops->select_level` then `ops->activate_level`.
  - `bsg_lod_stale(node, v)` delegates to `ops->is_stale` for
    BSG_NODE_LOD nodes; returns 0 for all other node kinds.
  - No producers yet; the function runs but is a no-op on production
    trees (no BSG_NODE_LOD nodes in the wild).

Phase L2 — wire the canonical update site in libdm  DONE
  - Added `bsg_lod_update((bsg_node *)v->bsg_root, v)` at the top of
    the `if (v->bsg_root)` block in `dm_draw_objs` in view.c, before
    the per-object traversal walk.
  - `s_update_callback` invocation in `_dm_draw_scene_obj_internal`
    remains in place for compat; both paths coexist while producers
    migrate (Phase L3).
  - `ged_test_lod_crossrun` PASS; all other drawing tests show no new
    failures vs baseline.

Phase L3 — migrate libged producers to emit LoD nodes
  Architecture (discovered during L0/L1/L2 session):
  - `_bview_state_attach_leaf` runs BEFORE geometry generation.  The mesh_obj
    / csg_obj fields and s_update_callback on the per-view 'vo' are NOT set
    at attach time; they are set by draw_scene() (called from the loop at
    dbi_state.cpp:3722-3728) which runs after all objects are attached.
  - Therefore the BSG_NODE_LOD wrapping cannot happen in
    `_bview_state_attach_leaf`.  It must happen AFTER the draw_scene loop.

  Implementation steps:
  1. Add `bsg_lod_node_insert_above(bsg_node *leaf, struct bview *v)` to
     `src/libbsg/lod_node.c`: detaches leaf from its parent children ptbl,
     creates a BSG_NODE_LOD node, inserts it in the parent's children in
     the same position, then adds leaf as level-0 child of the LoD node.
     Returns the new BSG_NODE_LOD node (or NULL on failure).
     Declare in `include/bsg/lod_ops.h`.

  2. Implement mesh-LoD and CSG-LoD ops adapters in
     `src/libged/bsg_ged_draw.c` (already the home of other BSG+GED
     integration code):
       struct _mesh_lod_state { struct bv_scene_obj *s; };
         select_level  : bv_obj_for_view(s,v) → bv_mesh_lod_view(vo,v,0);
                         returns 0 (single child in L3)
         activate_level: update cursor view_scale/perspective_flag/frame_rev
         is_stale      : cursor->view_scale != v->gv_scale ||
                         cursor->perspective_flag changes
         free          : bu_free(user_data)
       Similarly for CSG: select_level calls csg_wireframe_update(vo,v,0).

  3. After the draw_scene loop in BViewState::redraw (dbi_state.cpp:3728),
     add a wrapping pass:
       for each sp in objs:
         if (sp->mesh_obj || sp->csg_obj) AND sp->parent not a LOD node:
           lod = bsg_lod_node_insert_above((bsg_node *)sp, first_view)
           install ops + user_data on lod
           create cursor for each view in views

  4. In bsg_lod_node_insert_above, bump rev on the parent after insertion
     (bsg_bump_rev_node) and invalidate bbox (bsg_node_bbox_invalidate).

  Phase L3 coexistence with existing s_update_callback:
  - The per-view 'vo' still has s_update_callback set (BV_MESH_LOD flag
    on vo).  `_dm_draw_scene_obj_internal` still calls vo->s_update_callback
    via the children-recursion path.  bsg_lod_update also calls
    ops->select_level (which calls bv_mesh_lod_view on vo).  The double call
    is benign — bv_mesh_lod_view is idempotent for the same view state.
  - Full cleanup of the double-call is Phase L5+L6.

  Tests: `ged_test_lod_crossrun` (must remain green), `libbsg_lod_node`,
  `ged_test_bsg_view_obj`, `ged_test_drawing_lod` (images).

Phase L4 — remove per-view duplicate scene_objs for adaptive cases
  - For LoD-managed paths, stop populating `s->i->vobjs`.  The LoD
    node's per-view cursor replaces it.
  - Audit `bv_obj_for_view` callers: keep the function and the vobjs
    map for non-LoD per-view objects (edit highlights, view overlays);
    remove the LoD-path users.
  - Update `bv_scene_obj_bound` to consult the LoD node's currently
    selected child via the ops, not the legacy BV_MESH_LOD branch on
    a leaf.
  - Tests: full draw regression set, with extra attention to Quad
    view (multiple bviews sharing a draw root) and to memory growth.

Phase L5 — retire the BViewState::redraw LoD side pass
  - Delete the explicit `bv_mesh_lod_view` / `csg_wireframe_update`
    loop near `src/libged/dbi_state.cpp:3760`.
  - With L2+L3+L4 in place, redraw-on-zoom propagates LoD because
    the next `dm_draw_objs` runs `bsg_lod_update`.  No qged-only
    compensation should be needed.
  - Tests: full draw regression set; specifically verify zoom-driven
    redraws and headless image regeneration paths.

Phase L6 — retire `s_update_callback` and the BV_MESH_LOD/BV_CSG_LOD
            leaf flags
  - Once no producer sets `s_update_callback`, remove the field from
    `bv_scene_obj` and the call site in `_dm_draw_scene_obj_internal`.
  - Once no consumer tests `BV_MESH_LOD` / `BV_CSG_LOD` on a leaf
    (LoD-aware code goes through the LoD node), remove the flag bits
    or repurpose them as ops-internal markers only.
  - Simplify `bv_scene_obj_bound`: remove the leaf-side BV_MESH_LOD
    special case; aggregate bbox is then a pure tree walk.
  - Tests: full draw regression set; this phase is mostly mechanical
    once L5 is green.

Phase L7 — image-level parity and front-end verification
  - Re-run `ged_test_drawing_lod` and `ged_test_lod_crossrun` for
    image diffs.
  - Re-check the known weak spots that LoD ambiguity may have been
    masking:
      * shaded mode 1 with LoD disabled,
      * hidden-line mode 4,
      * mixed draw modes on the same path.
  - Verify mged, Archer, and qged produce visually identical output
    for adaptive zoom, multi-view Quad, and headless image runs.
  - Only after this is solid, return to the open backend default
    decision (Priority 4 below).

Test surface to keep green at every phase
-----------------------------------------
- `ged_test_bsg_view_obj`         (LoD node lifecycle, cursor)
- `ged_test_drawing_basic`        (no-LoD baseline)
- `ged_test_drawing_faceplate`    (view-only objects unaffected)
- `ged_test_drawing_lod`          (image diffs for mesh + CSG LoD)
- `ged_test_lod_crossrun`         (cross-run cache reuse)
- `ged_test_mged_shaded_mode_bsg` (shaded mode + LoD interaction)
- `ged_test_bsg_parity`, `ged_test_bsg_quad_parity`
                                  (no regression in non-LoD paths)

Deferred / non-goals for this work package
------------------------------------------
- Backend default decision (the open dm-qtgl vs dm-swrast benchmark
  question) is still deferred until after LoD parity lands.  See
  Priority 4 below.
- Bigger Inventor-style ideas (e.g. SoCache, traversal-state caches,
  full action pattern) are explicitly out of scope.  We are borrowing
  the *node-as-selector* idea and the *one-traversal* invariant, not
  rebuilding the action framework.
- Selection-highlight rework is unaffected; the LoD redesign is
  orthogonal to `gd_illum_sensor` / `gd_illum_rev`.

Prioritized remaining work
--------------------------
Priority 1 — execute the LoD redesign above (Phases L0–L7).
  This is the next major work package.

Priority 2 — close image-level parity gaps once LoD is unambiguous:
  shaded mode 1 with LoD disabled, hidden-line mode 4, LoD image
  regressions.  These are largely re-tests after L7.

Priority 3 — verify front-end parity (qged / mged / Archer) for
  draw, erase, redraw, selection-highlight, adaptive zoom, mixed
  draw modes on the same path.  L4–L5 should make this fall out
  naturally.

Priority 4 — backend policy / default-backend decision.  Open, but
  not a blocker for the LoD work and not a blocker for declaring the
  qged/mged stack merge complete.

Recommended next steps
----------------------
1. Treat the LoD redesign (Phases L0–L7) as the next work package.
2. Land L0 + L1 first; they are additive and risk-free (no producers
   touch BSG_NODE_LOD yet).
3. Land L2 next as a no-op wiring change so the call site is in
   place before any producer migrates.
4. Migrate producers (L3) one primitive family at a time if needed
   (mesh first, then CSG), keeping the legacy `s_update_callback`
   path live during the transition.
5. Once L3 is complete for all adaptive producers, land L4 to drop
   the per-view duplicate scene objects, then L5 to drop the
   BViewState::redraw side pass.
6. L6 is the cleanup that finalises the design: removing
   `s_update_callback` and the leaf-side BV_MESH_LOD/BV_CSG_LOD
   flags.
7. L7 is the parity / image-diff phase; only after it is green
   should attention return to the deferred backend default decision.

What not to undo
----------------
- Do not make gv_objs DB tables authoritative again.
- Do not move qged's higher-level state model into libbsg.
- Do not add backend-specific fields back onto `bv_scene_obj`.
- Do not add a second, parallel LoD update path once the shared one is
  in place.  After Phase L2, `dm_draw_objs` calling `bsg_lod_update`
  must remain the single update site.
- Do not push LoD selection logic back down into individual scene-object
  leaves or per-leaf callbacks.  The LoD node owns selection; leaves
  are pure representations.
- Do not reintroduce per-view duplicate `bv_scene_obj` subtrees for
  adaptive geometry once Phase L4 has removed them.  Per-view state
  for LoD is a cursor on the LoD node, not a duplicate subtree.
- Do not re-fuse "is this a DB object?" with "is this an LoD leaf?"
  on `bv_scene_obj`.  Identity belongs to tree placement; LoD
  awareness belongs to the LoD node kind.
- Do not judge success by qged alone; the target is one stack that works
  cleanly for qged and for mged/Archer.
