Drawing Modernization Implementation Guide
==========================================

Purpose
-------
This document is the implementation guide for completing BRL-CAD's drawing
modernization before an Obol backend lands.  It supersedes the earlier design
pass: the proposals below are now requirements, and each phase lists concrete,
ordered work items that take the codebase from the current partial state to a
production-ready OpenInventor-style BSG scene graph that GL, swrast, qtgl and
Obol all consume as adapters.

The guide is intended to be picked up across multiple sessions.  Each phase is
self-contained, has explicit entry preconditions, ordered tasks, exit criteria,
and a validation list pulled from the matrix at the end of the document.

Scope and non-goals
-------------------
In scope:
- Finish the typed BSG payload model and migrate every UI/drawing consumer off
  raw `s_vlist`, `s_i_data`, `draw_data`, and `BSG_ADD_VLIST`/`BSG_FREE_VLIST`.
- Finish draw-intent semantics and route every database draw/erase/report/
  export/raytrace command through draw-intent actions.
- Finish pick, snap, and measurement actions and migrate every selection,
  illumination, snap, and measurement tool onto typed records.
- Complete HUD and overlay scene graphs and remove libdm's faceplate epilogue.
- Drive 100% of production scene rendering through the backend adapter contract
  and retire libdm-owned traversal/transparency/LoD policy.
- Promote the appearance/material resolution to a BSG action and remove ad hoc
  appearance decisions from libdm and consumers.
- Promote camera, lights, and render settings to first-class scene/render state.
- Generalize the backend cache lifecycle so the adapter contract is the single
  caching boundary.
- Make `bsg_node` opaque, retire the public `BV_*` compatibility aliases that
  are no longer required by external headers, and finalize the public API.

Out of scope (deferred to the Obol integration project):
- Implementing the Obol backend itself.
- Migrating raw `BSG_ADD_VLIST`/`BSG_FREE_VLIST` usage inside librt primitive
  plotters and ray-tracing utilities (these stay as VLIST-payload producers
  unless a tool-level migration touches them).
- Designing or implementing a new shading/lighting model beyond the existing
  bsg_light snapshots.

Vocabulary
----------
This guide uses the OpenInventor-style vocabulary defined in
`brlcad/doc/bsg_vocabulary.md`: scene root, draw intent, group, transform,
shape, payload, material, appearance, selection, pick, camera, light, HUD root,
overlay role, render request, render item, and backend adapter.  Do not
reintroduce display-list, solid-list, scene-object, view-object, or `BV_*`
terms in new code or comments.

Modernization goals (acceptance reference)
==========================================
The phases below collectively deliver these end-state properties.  Each phase
exit criterion is derived from one or more of these goals; review them when
deciding whether a phase is truly complete.

G1.  Every drawing producer creates typed BSG payloads through a builder API.
     `BSG_ADD_VLIST`/`BSG_FREE_VLIST` survive only inside librt primitive
     plotters and the VLIST payload internals.
G2.  Every renderer/consumer of payload data goes through payload accessors
     (`pl_bounds`, `pl_export`, `pl_pick`, `pl_snap`, `pl_backend_prepare`,
     revision/type query).  No consumer inspects `s_vlist`, `s_i_data`,
     `draw_data`, or other former bsg_node fields.
G3.  Every database draw, erase, who, how, rt, nirt, gqa, saveview, plot, ps,
     png, and bot_dump command operates on draw-intent actions; intent is
     never reconstructed from child tables or names.
G4.  Selection lives in `bsg_selection`.  Picking returns typed
     `bsg_pick_record`s.  Snap/measurement queries return typed records.
     Highlighting is a derived appearance layer, not a node flag.
G5.  Faceplate/HUD output is BSG scene nodes with HUD payloads; libdm draws
     them by executing render items.  Overlays carry typed role and lifecycle
     metadata; tools replace/clear their own overlays through the lifecycle
     API.
G6.  All production rendering for GL, swrast, qtgl (and the future Obol
     backend) flows through `bsg_render_request_execute` with backend-adapter
     callbacks.  libdm owns only display-manager operations and backend
     primitive draw calls.
G7.  Material/appearance is resolved by a BSG action and stored in
     `bsg_render_item`; backends never recombine source material with
     selection/highlight/transparency state.
G8.  Camera, lights, and render settings are first-class BSG state attached to
     views.  Saved views, multi-view layouts, and shared scene roots use the
     same API.
G9.  Backend caches react to payload, appearance, transform, and render-mode
     revisions through the adapter contract.  Backend handles never leak into
     public node APIs.
G10. `bsg_node` is opaque; the public API exposes the vocabulary nouns from
     `bsg_vocabulary.md`; legacy `BV_*` aliases survive only in clearly
     marked compatibility bridges with a documented removal plan.

Implementation phases
=====================
Phases are independent in concept but have data dependencies in practice.
Recommended execution order: D1 → D2 → D3 → D4 → D5 → D6 → D7, but D2/D3 may
overlap, and Phase D5 step 1 (resolved appearance) may begin once D1's payload
revision and bounds hooks exist.

- All pick/snap/measure consumers use typed records; no UI/tool code converts

- `bu_ptbl`-of-`bsg_node*` selection storage is gone outside the
  documented compatibility shim in `bsg_pick_result_to_ptbl`.

Phase D4 — HUD scene root and overlay policy
--------------------------------------------
Goal: G5, partial G6.

Preconditions: D1 HUD_TEXT/IMAGE/FRAMEBUFFER/GRID/AXES builders.

Tasks:
1. Realize HUD payloads.  For each HUD feature slot in `bsg/hud.h`, replace
   the libdm rasterizer in `dm_draw_faceplate` with a builder that fills the
   feature's HUD node with the correct payload:
     a. CENTER_DOT → HUD_TEXT or a tiny LINE_SET in screen space.
     b. MODEL_AXES → AXES payload anchored in model space.
     c. VIEW_AXES → AXES payload anchored in screen corner.
     d. VIEW_SCALE → LINE_SET + HUD_TEXT.
     e. ADC → LINE_SET + HUD_TEXT.
     f. GRID → GRID payload.
     g. RECT (rubber band) → LINE_SET in screen space.
     h. VIEW_PARAMS → HUD_TEXT block.
     i. FRAMEBUFFER → FRAMEBUFFER payload with underlay/overlay role.
2. Overlay role/lifecycle expansion.  Extend `include/bsg/hud.h` (or split
   `include/bsg/overlay.h` if size warrants) with:
     a. Roles: EDIT_HANDLE, MEASURE, SELECTION_RUBBER_BAND, SNAP_GUIDE,
        COMMAND_RESULT, DIAGNOSTIC, TCL_ADORNMENT, POLYGON_EDIT, SKETCH_EDIT,
        USER_ANNOTATION (in addition to MODEL/SCREEN/XRAY).
     b. Lifecycle policy enum: PERSISTENT, PER_COMMAND, PER_TOOL, PER_VIEW,
        SHARED_VIEW_SET, AUTO_REMOVE_ON_SOURCE_CHANGE.
     c. Ordering policy enum: MODEL_OVERLAY, SCREEN_OVERLAY,
        XRAY_OVERLAY, POST_TRANSPARENT_OVERLAY.
     d. Tool-ownership API: `bsg_overlay_register_owner`,
        `bsg_overlay_replace`, `bsg_overlay_clear_owned`,
        `bsg_overlay_query_by_role`.
3. Lifecycle driver.  Hook auto-remove-on-source-change into the draw-intent
   revalidate path from D2.  Tools call `bsg_overlay_replace` to refresh per-
   command overlays without naming conventions.
4. Render-phase mapping.  The HUD pass must execute through
   `bsg_render_request_execute` (Phase D5 step 2).  Each HUD feature carries
   the documented `BSG_RENDER_PHASE_HUD` + `bsg_hud_node_meta::sort_order`.
   Framebuffer underlay/overlay carries `BSG_HUD_FEATURE_FRAMEBUFFER` ordering
   so the underlay renders first and the overlay last.
5. Consumer migration:
     a. Tcl adornments (`libtclcad/tclcad_obj.c`,
        `libtclcad/bsg_move_helpers.h` callers) → overlay nodes with the
        TCL_ADORNMENT role.
     b. qged measurement/selection/edit plugin overlays → typed roles +
        lifecycle.
     c. MGED ADC, grid, axes, params → migrate to HUD nodes built by the
        new builders rather than direct libdm calls.
6. Retire `dm_draw_faceplate`.  Once step 1 and step 4 are in place, delete
   the function and its callers from `libdm/view.c`.

Exit criteria:
- `dm_draw_faceplate` does not exist; HUD output flows through render items.
- `bsg_overlay_query_by_role(role)` enumerates a tool's overlays for replace/
  clear without name matching.
- HUD structural tests cover all 9 features and all expanded overlay roles.

Phase D5 — Render pipeline, resolved appearance, and backend adapter
--------------------------------------------------------------------
Goal: G6, G7, G9, partial G8.

Preconditions: D4 step 1 (HUD payloads exist so the render path can drive
them); D3 selection finalisation (so highlight is sourced from
`bsg_selection`).

Tasks:
1. Resolved appearance action.  Add `include/bsg/appearance_action.h`:
     a. `bsg_appearance_resolve(const struct bsg_view *v, const bsg_node *path,
        struct bsg_resolved_appearance *out)` accumulating source material,
        command override, inherited group settings, selection/edit state, and
        display mode along the scene path.
     b. Store the result on `bsg_render_item` (extend the struct with the
        resolved appearance fields and a revision tag).
     c. Provide `bsg_appearance_layer` enum for highlight, edit preview,
        ghosting, hidden-line, transparency.  Layers compose during resolve.
2. Move scene traversal into libbsg.  Port `_bsg_view_traverse_impl` from
   `libdm/view.c` into `src/libbsg/render.c` as the production
   implementation of `bsg_render_request_execute`.  Traversal must cover:
     a. visibility filtering;
     b. view-scope filtering;
     c. transform accumulation;
     d. LoD active-level selection (move the LoD update timing here from
        libdm/libged callers);
     e. transparency sorting (back-to-front within
        `BSG_RENDER_PHASE_TRANSPARENT`);
     f. resolved appearance per item;
     g. overlay ordering by role/lifecycle;
     h. HUD pass after the 3D scene.
3. Adapter parity.  Replace the remaining direct libdm draw calls in
   `dm_draw_objs` and the GL-family `dm_backend_draw_obj` paths with adapter
   callbacks that consume `bsg_render_item` plus resolved appearance.  Audit
   `dm-glx`, `dm-swrast`, `dm-qtgl`, and `dm-plot`/`dm-ps`/`dm-txt` for any
   policy decisions that are now redundant.
4. Render settings object.  Add `include/bsg/render_settings.h` collecting
   draw mode, hidden-line, zclip, transparency policy, LoD policy,
   framebuffer mode, and HUD enablement.  Attach to `bsg_view` and consume
   from the render request rather than reading scattered `bsg_view_settings`
   fields during traversal.
5. Camera and light bindings.  Promote camera snapshots to a `bsg_camera_node`
   that can be bound to a view (`bsg_view_set_camera_node`) and saved/
   restored by the view command.  Promote lights to a `bsg_light_set` that
   render requests consume.  Multi-view qged binds a shared scene root with
   per-view camera/HUD/overlay scopes.
6. Backend cache lifecycle.  Specify the cache-key inputs in
   `include/bsg/backend_adapter.h`: payload revision, appearance revision,
   transform path revision, render-mode revision.  Adapter `invalidate`
   receives a typed reason mask.  Audit GL/swrast/qtgl backend caches and
   ensure they invalidate on the correct revision changes.
7. Consumer migration:
     a. Remove all `dm_*` policy calls (transparency pass, LoD update,
        faceplate epilogue) from `libdm/view.c` that traversal now owns.
     b. Migrate `libged/view/objs.cpp`, `qged_view_settings` to write through
        the render-settings object.
     c. Migrate any caller of `bv_set_scene_set` to the bound camera/HUD
        scopes for per-view state.
8. Tests:
     a. `libbsg_appearance_resolve` (path accumulation, layer composition).
     b. `libbsg_render` — extend with transparency sort, LoD active-level,
        overlay ordering, HUD pass.
     c. `libbsg_backend_adapter` — invalidation reason coverage.
     d. `ged_test_drawing_faceplate`, `ged_test_drawing_lod`,
        `ged_test_drawing_basic`, `ged_test_bsg_view_obj`,
        `ged_test_qged_swrast`, `ged_test_mged_bsg`,
        `ged_test_mged_shaded_mode_bsg`, `ged_test_rtwizard_bsg`,
        `ged_test_bsg_parity`, `ged_test_bsg_quad_parity` all pass.

Exit criteria:
- `_bsg_view_traverse_impl` does not exist in libdm.
- `bsg_render_item` carries resolved appearance; backends never recombine.
- Camera, lights, and render settings are read from the render request, not
  from `bsg_view`/`bsg_view_settings` directly during draw.
- Backend invalidations fire for the correct revision changes (tested).

Phase D7 — Compatibility isolation and public API cleanup
---------------------------------------------------------
Goal: G10.

Preconditions: D1–D6 complete (so the public API surface is stable).

Tasks:
1. Make `bsg_node` opaque.
     a. Move the struct definition into `src/libbsg/bsg_private.h`.
     b. Replace remaining public-header field references with accessor calls
        (scan all of `brlcad/include` and `brlcad/src`).
     c. Add accessors for any field that has no public equivalent; refuse to
        add accessors that only exist to keep legacy code compiling — port
        the legacy code instead.
2. Public alias retirement.
     a. Inventory the `BV_*` aliases in `include/bsg/defines.h` and other
        `include/bv/*` headers.
     b. For each alias, classify as (i) keep as documented compatibility
        bridge with a deprecation note, (ii) move into a single
        `include/bsg/legacy_compat.h` header guarded by
        `BSG_ENABLE_LEGACY_BV_ALIASES`, or (iii) remove now and update
        callers.
     c. Provide a one-page deprecation guide in `bsg_vocabulary.md` mapping
        each retired `BV_*` name to its `BSG_*` replacement.
3. File renames.  Where filenames still reference the libbv era
   (`view_sets.cpp`, `bv_*.c`, etc.), rename to BSG-aligned names or split
   responsibilities.  Update `CMakeLists.txt` and includes.
4. Comment and TODO sweep.  Final pass that removes legacy comments missed
   during D0 step 1 and converts surviving `TODO(bsg-modernize)` markers into
   issues or deletes them.
5. Documentation.  Refresh `bsg_vocabulary.md` and add a developer guide
   `brlcad/doc/bsg_drawing_api.md` describing the end-state API surface
   (payload builders, draw-intent actions, pick/snap/measure actions, HUD
   and overlay APIs, render request/adapter contract, appearance resolve,
   render settings, camera/light bindings).
6. Cross-cutting compatibility bridges.  Any compatibility shim that cannot
   be removed before Obol must be tagged `/* legacy-compat: remove with
   <issue/PR ref> after Obol parity */` and listed in
   `bsg_drawing_api.md`'s "Scheduled removals" section.

Exit criteria:
- `struct bsg_node` is not visible to public headers.
- Public headers no longer declare new `BV_*` symbols; remaining aliases
  live in a single compatibility header with a documented removal plan.
- `brlcad/doc/bsg_drawing_api.md` exists and matches the implementation.
- All scheduled removals have ticket/PR references.

Definition of done
==================
The drawing modernization is complete and ready to host the Obol backend when
all of the following hold:

1. Goals G1-G10 are met and the corresponding exit criteria for D0-D7 are
   demonstrated.
2. The full validation matrix above passes on a Qt-enabled build.
3. `brlcad/doc/bsg_vocabulary.md` and `brlcad/doc/bsg_drawing_api.md` describe
   the public API used by every consumer touched by D1-D7, and no consumer
   relies on a noun outside that vocabulary.
4. Remaining compatibility shims are documented with explicit removal owners
   in `bsg_drawing_api.md`.
5. Adding the Obol backend requires implementing only the documented
   `bsg_backend_adapter` callbacks plus payload prepare hooks — no changes
   to traversal, selection, picking, snap, measurement, HUD, overlay, draw-
   intent, appearance-resolution, or render-settings code.
