Drawing Modernization Implementation Guide
==========================================

Purpose
-------
This document is the implementation guide for completing BRL-CAD's drawing
modernization before an Obol backend lands.  It supersedes the earlier design
pass: the proposals below are now requirements, and each phase lists concrete,
ordered work items that take the codebase from the current partial state to a
production-ready OpenInventor-style BSG scene graph that GL, swrast, qtgl and
Obol all consume as adapters.

The guide is intended to be picked up across multiple sessions.  Each phase is
self-contained, has explicit entry preconditions, ordered tasks, exit criteria,
and a validation list pulled from the matrix at the end of the document.

Scope and non-goals
-------------------
In scope:
- Finish the typed BSG payload model and migrate every UI/drawing consumer off
  raw `s_vlist`, `s_i_data`, `draw_data`, and `BSG_ADD_VLIST`/`BSG_FREE_VLIST`.
- Finish draw-intent semantics and route every database draw/erase/report/
  export/raytrace command through draw-intent actions.
- Finish pick, snap, and measurement actions and migrate every selection,
  illumination, snap, and measurement tool onto typed records.
- Complete HUD and overlay scene graphs and remove libdm's faceplate epilogue.
- Drive 100% of production scene rendering through the backend adapter contract
  and retire libdm-owned traversal/transparency/LoD policy.
- Promote the appearance/material resolution to a BSG action and remove ad hoc
  appearance decisions from libdm and consumers.
- Promote camera, lights, and render settings to first-class scene/render state.
- Generalize the backend cache lifecycle so the adapter contract is the single
  caching boundary.
- Make `bsg_node` opaque, retire the public `BV_*` compatibility aliases that
  are no longer required by external headers, and finalize the public API.

Out of scope (deferred to the Obol integration project):
- Implementing the Obol backend itself.
- Migrating raw `BSG_ADD_VLIST`/`BSG_FREE_VLIST` usage inside librt primitive
  plotters and ray-tracing utilities (these stay as VLIST-payload producers
  unless a tool-level migration touches them).
- Designing or implementing a new shading/lighting model beyond the existing
  bsg_light snapshots.

Vocabulary
----------
This guide uses the OpenInventor-style vocabulary defined in
`brlcad/doc/bsg_vocabulary.md`: scene root, draw intent, group, transform,
shape, payload, material, appearance, selection, pick, camera, light, HUD root,
overlay role, render request, render item, and backend adapter.  Do not
reintroduce display-list, solid-list, scene-object, view-object, or `BV_*`
terms in new code or comments.

Modernization goals (acceptance reference)
==========================================
The phases below collectively deliver these end-state properties.  Each phase
exit criterion is derived from one or more of these goals; review them when
deciding whether a phase is truly complete.

G1.  Every drawing producer creates typed BSG payloads through a builder API.
     `BSG_ADD_VLIST`/`BSG_FREE_VLIST` survive only inside librt primitive
     plotters and the VLIST payload internals.
G2.  Every renderer/consumer of payload data goes through payload accessors
     (`pl_bounds`, `pl_export`, `pl_pick`, `pl_snap`, `pl_backend_prepare`,
     revision/type query).  No consumer inspects `s_vlist`, `s_i_data`,
     `draw_data`, or other former bsg_node fields.
G3.  Every database draw, erase, who, how, rt, nirt, gqa, saveview, plot, ps,
     png, and bot_dump command operates on draw-intent actions; intent is
     never reconstructed from child tables or names.
G4.  Selection lives in `bsg_selection`.  Picking returns typed
     `bsg_pick_record`s.  Snap/measurement queries return typed records.
     Highlighting is a derived appearance layer, not a node flag.
G5.  Faceplate/HUD output is BSG scene nodes with HUD payloads; libdm draws
     them by executing render items.  Overlays carry typed role and lifecycle
     metadata; tools replace/clear their own overlays through the lifecycle
     API.
G6.  All production rendering for GL, swrast, qtgl (and the future Obol
     backend) flows through `bsg_render_request_execute` with backend-adapter
     callbacks.  libdm owns only display-manager operations and backend
     primitive draw calls.
G7.  Material/appearance is resolved by a BSG action and stored in
     `bsg_render_item`; backends never recombine source material with
     selection/highlight/transparency state.
G8.  Camera, lights, and render settings are first-class BSG state attached to
     views.  Saved views, multi-view layouts, and shared scene roots use the
     same API.
G9.  Backend caches react to payload, appearance, transform, and render-mode
     revisions through the adapter contract.  Backend handles never leak into
     public node APIs.
G10. `bsg_node` is opaque; the public API exposes the vocabulary nouns from
     `bsg_vocabulary.md`; legacy `BV_*` aliases survive only in clearly
     marked compatibility bridges with a documented removal plan.

Implementation phases
=====================
Phases are independent in concept but have data dependencies in practice.
Recommended execution order: D1 → D2 → D3 → D4 → D5 → D6 → D7, but D2/D3 may
overlap, and Phase D5 step 1 (resolved appearance) may begin once D1's payload
revision and bounds hooks exist.
