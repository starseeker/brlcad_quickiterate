BV_SCENE_OBJ TO BSG FULL MIGRATION PLAN
======================================

Purpose
-------
Capture a complete migration plan for removing the remaining structural
dependency on struct bv_scene_obj as the effective scene-graph node backing
store, with particular focus on the remaining bsg_settings coupling and the
possibility of fully retiring bv_scene_obj in favor of first-class BSG types.


Current Situation Summary
-------------------------
1. bsg_settings is logically a BSG concept, but its struct definition still
   lives in include/bv/defines.h.

2. The immediate reason is storage and header layering:
   - struct bv_scene_obj embeds:
       struct bsg_settings *s_os;
       struct bsg_settings  s_local_os;
   - include/bsg/defines.h includes include/bv/defines.h.
   - include/bsg/settings.h includes include/bsg/defines.h.
   This means a simple move of struct bsg_settings into a libbsg header would
   create a circular dependency unless the storage or header layout changes.

3. The API migration is only partially blocked by callers.  Most high-level
   traversal code already uses typed BSG settings accessors, but some libbv,
   libdm, and libged code still touches bv_scene_obj settings storage directly.

4. The larger migration question is broader than settings.  bsg_settings is one
   example of a general problem: bsg_node is still physically embedded inside
   bv_scene_obj, and many subsystems still assume bv_scene_obj is the concrete
   node/container/payload object.


Primary Goal
------------
Arrive at a design where:

- BSG owns its node, material, appearance, payload, identity, and traversal
  contracts directly.
- bsg_settings either disappears entirely or becomes an internal transitional
  compatibility type that is no longer defined in bv/defines.h.
- libdm, libged, qged, mged, libqtcad, and libtclcad consume BSG APIs instead
  of raw bv_scene_obj fields.
- bv_scene_obj becomes either:
  A) a temporary compatibility wrapper with no unique semantic ownership, or
  B) removable entirely once the remaining raw-storage assumptions are gone.


Non-Goals
---------
- Do not attempt a big-bang rewrite.
- Do not break existing rendering behavior, edit workflows, or display-list
  lifecycles while refactoring ownership.
- Do not remove compatibility fields before equivalent BSG APIs exist and have
  been adopted by all non-test callers.


Key Constraints and Blockers
----------------------------
1. Header dependency cycle
   bsg/defines.h currently depends on bv/defines.h for struct bsg_node and the
   current compatibility layout.

2. Inline storage
   Embedded fields in bv_scene_obj require complete type definitions at header
   parse time, preventing simple forward-declaration-based decoupling.

3. Remaining raw field access
   The raw field inventory shows that many subsystems still touch bv_scene_obj
   fields directly beyond settings: names, paths, transforms, payloads, flags,
   color, backend cache, and custom data.

4. Transitional mixed ownership
   Some concepts already have BSG APIs but still write back into legacy
   bv_scene_obj fields for compatibility.

5. Unsettled semantic homes
   Not every bsg_settings field has a final destination yet:
   - draw_mode -> bsg_appearance
   - line_width -> bsg_appearance
   - arrow_tip_length / arrow_tip_width -> bsg_appearance
   - transparency -> material or appearance, depending on final policy
   - color_override / color -> bsg_material
   - draw_solid_lines_only / draw_non_subtract_only -> appearance or draw policy
   - mixed_modes -> still needs a clear permanent home


Migration Strategy Overview
---------------------------
Use a staged migration with two tracks:

Track 1: Remove the bsg_settings dependency on bv/defines.h.
Track 2: Remove bv_scene_obj as the concrete backing store assumption.

Track 1 can deliver incremental value even if Track 2 takes longer, but Track 2
is the cleanest long-term solution and should inform the API choices made in
Track 1.


Recommended End State
---------------------
Recommended target architecture:

1. struct bsg_node becomes the concrete first-class scene-graph node type.

2. Node-associated state is owned by BSG abstractions:
   - identity
   - material
   - appearance
   - payload
   - transform
   - selection/highlight state
   - renderer/backend compatibility hooks where still needed

3. bv_scene_obj becomes a compatibility layer only, then is retired.

4. bsg_settings is retired as a public structural dependency:
   - either replaced entirely by material + appearance + draw policy APIs, or
   - kept only as an internal compatibility snapshot outside bv/defines.h.


Phase 0 - Inventory Refresh and Guardrails
------------------------------------------
Objective:
Refresh the raw-field inventory and define the migration boundary before moving
storage.

Tasks:
- Re-run the raw field inventory search and update counts/files if they have
  drifted.
- Classify each raw field as one of:
  - already has a BSG API
  - needs a BSG API
  - compatibility-only and can remain temporarily
  - obsolete and removable
- Identify every site still touching:
  - s_os / s_local_os
  - s_path
  - dp
  - s_mat
  - s_i_data
  - s_vlist / s_vlen
  - s_color / s_color_rev
  - s_flag / s_iflag / s_force_draw
  - s_v
  - s_backend

Deliverables:
- Updated raw field inventory
- A field-to-BSG-owner mapping table
- A list of compatibility-only fields that must remain until final cutover

Exit criteria:
- No unknown raw-field ownership remains.


Phase 1 - Finish the Settings Semantic Split
--------------------------------------------
Objective:
Stop treating bsg_settings as the long-term semantic API.

Tasks:
- Define the permanent home of every bsg_settings field.
- Move callers away from thinking in terms of one monolithic settings blob.
- Decide where mixed_modes belongs:
  - bsg_appearance
  - a producer/draw request policy object
  - a renderer/draw command option

Recommended direction:
- Appearance:
  draw_mode, line_width, line_style/dash policy, inherit_settings,
  arrow_tip_length, arrow_tip_width, draw_solid_lines_only,
  draw_non_subtract_only
- Material:
  transparency, color override, explicit color source
- Producer/render policy:
  mixed_modes

Tasks by library:
- libdm: prefer bsg_appearance_get/material_get where possible instead of
  reading raw settings snapshots.
- libged: replace remaining settings-centric flows with appearance/material
  logic where no bundle copy is required.
- libbv: isolate any remaining bundle-copy/reset logic behind compatibility
  helpers rather than public structure ownership.

Exit criteria:
- No new code relies on bsg_settings as the canonical semantic type.


Phase 2 - Eliminate Remaining Raw s_os/s_local_os Consumers
-----------------------------------------------------------
Objective:
Remove direct settings-storage reads/writes from callers.

Known remaining direct-use areas to retire first:

libbv:
- snap.c: line width for snap tolerance can move to bsg_node_appearance_get().
- util.cpp: reset/default/sync logic should be routed through BSG-owned helper
  functions or compatibility shims.
- hash.c: local/effective settings hashing should move behind a libbsg or compat
  hashing helper if still needed.

libdm:
- dm-gl_lod.cpp: replace raw draw_mode/transparency reads with resolved
  appearance/material queries or with pre-resolved render-action state.
- X/dm-X.c: replace draw_mode raw check with appearance query.

libged:
- draw.cpp: replace raw draw_mode, color_override, draw_non_subtract_only, and
  draw_solid_lines_only accesses with appearance/material APIs.
- bsg_ged_draw.c: replace direct assignments to sp->s_os with BSG setter calls.

Tasks:
- Provide missing BSG getters/setters needed by those callers.
- Convert each caller and validate behavior after each cluster.
- Add regression tests where existing BSG test coverage is missing.

Exit criteria:
- Non-test code outside compatibility modules no longer reads or writes
  s_os/s_local_os directly.


Phase 3 - Introduce a Compatibility Header Boundary
--------------------------------------------------
Objective:
Break the header cycle that keeps bsg_settings in bv/defines.h.

Options:

Option A - Intermediate shared header
- Move struct bsg_settings to a neutral header that both bv and bsg can include.
- Keep storage in bv_scene_obj temporarily.
- Lowest immediate risk.

Option B - Compatibility header split
- Keep BSG-facing type definitions in include/bsg/.
- Move bv compatibility storage declarations into a dedicated compatibility
  header, not the core public BSG headers.

Option C - Remove inline storage first
- Replace s_local_os embedded storage with opaque/heap-backed compatibility
  storage so bv/defines.h no longer needs the full struct definition.
- This is the cleanest architectural move, but requires more lifecycle changes.

Recommended order:
- Use Option A or B only as a transitional step if needed to reduce risk.
- Prefer converging toward Option C as part of the larger bv_scene_obj removal.

Exit criteria:
- struct bsg_settings is no longer defined in include/bv/defines.h.


Phase 4 - Replace bv_scene_obj-Owned Settings Storage
----------------------------------------------------
Objective:
Make settings/appearance/material state BSG-owned rather than bv_scene_obj-owned.

Tasks:
- Remove the assumption that bv_scene_obj owns:
  - s_os
  - s_local_os
  - s_inherit_settings
- Store compatibility state in one of:
  - BSG node sidecar storage
  - appearance/material sidecars only
  - a dedicated compatibility extension object

Recommended direction:
- Eliminate s_local_os as embedded storage.
- Resolve inherit_settings through bsg_appearance.
- Resolve color override and transparency through bsg_material.
- Retire bsg_settings_sync from public usage patterns once bundle copying is no
  longer the normal mechanism.

Possible temporary design:
- A compat object owned by bsg_node_core that exposes legacy snapshots only for
  transition code.

Exit criteria:
- bv_scene_obj no longer uniquely owns settings state.


Phase 5 - Promote BSG Node Ownership Over Remaining Raw Fields
--------------------------------------------------------------
Objective:
Systematically migrate all remaining bv_scene_obj raw semantics to BSG APIs.

Work items by concept:

Identity/path/source metadata
- s_name -> bsg_node_name()/set_name()
- s_path -> bsg_identity source path APIs
- dp -> bsg_identity/source metadata APIs

Transform/view ownership
- s_mat -> bsg_node_transform_get/set()
- s_v -> BSG view-scope semantics and edit-context APIs

Payload/custom data
- s_i_data -> typed payload/aux data APIs
- s_vlist / s_vlen -> vlist payload APIs

Visibility/highlight
- s_flag -> bsg_node_visible()/set_visible()
- s_force_draw -> bsg_node_force_draw()/set_force_draw()
- s_iflag -> BSG selection/highlight compatibility APIs

Material/appearance
- s_color / s_color_rev -> bsg_material and node revision APIs
- s_soldash / s_arrow -> bsg_appearance or overlay appearance APIs

Renderer cache
- s_backend -> explicit renderer-owned backend attachment API

Lifecycle
- s_update_callback / s_free_callback -> node payload lifecycle/update hooks

Exit criteria:
- All non-test callers use BSG APIs instead of raw bv_scene_obj fields for
  semantics.


Phase 6 - Create a First-Class BSG Allocation and Lifecycle Model
-----------------------------------------------------------------
Objective:
Stop requiring libbv allocation/reset utilities as the owner of scene nodes.

Tasks:
- Introduce BSG-native node creation/destruction APIs for all major node kinds.
- Ensure BSG owns:
  - allocation
  - child tables
  - core init/release
  - payload teardown
  - renderer hook cleanup
- Rework compatibility code so bv_obj_reset()/bv_obj_put() become wrappers over
  BSG lifecycle, not the root ownership mechanism.

Requirements:
- No caller should need to know whether the node originated as a bv_scene_obj.
- Compatibility cleanup must remain safe for legacy call sites until cutover.

Exit criteria:
- New code can allocate, manipulate, and free scene nodes entirely through BSG.


Phase 7 - Narrow bv_scene_obj to a Compatibility Wrapper
-------------------------------------------------------
Objective:
Shrink bv_scene_obj until it contains no unique public semantics.

Tasks:
- Remove or deprecate direct public dependence on struct layout.
- Move remaining compatibility-only fields behind opaque pointers where
  practical.
- Limit direct uses of bv_scene_obj to:
  - compatibility bridges
  - legacy adapters
  - isolated rendering shims not yet ported

Recommended milestone:
- Compile most of libdm/libged/qged against BSG APIs without requiring direct
  access to bv_scene_obj internals.

Exit criteria:
- bv_scene_obj is a transitional wrapper, not the semantic model.


Phase 8 - Final Cutover: Remove bv_scene_obj as the Backing Store
-----------------------------------------------------------------
Objective:
Make bsg_node and related BSG-owned data structures the only real scene-graph
storage model.

Tasks:
- Remove the first-member embedding dependency:
  current model: bv_scene_obj contains struct bsg_node as first member
  target model: BSG nodes exist independently
- Replace casts between bsg_node * and bv_scene_obj * with explicit conversion
  helpers only in temporary compatibility code.
- Update renderer and editor code to consume bsg_node/payload/material/
  appearance abstractions directly.
- Retire remaining compatibility-only allocation/reset paths.

Compatibility plan:
- If needed, keep a short-lived adapter that can wrap a bsg_node in a legacy
  bv_scene_obj facade for old API entry points.

Exit criteria:
- Non-compat production code no longer depends on struct bv_scene_obj.


Phase 9 - Retire Transitional APIs and Data Structures
-----------------------------------------------------
Objective:
Remove migration scaffolding once callers are cut over.

Candidates for retirement:
- bsg_settings as a public structural type if appearance/material/policy fully
  replace it
- legacy conversion helpers
- raw field compatibility macros
- bv_scene_obj-specific wrappers that only forward into BSG
- redundant sync/hash/reset helpers that exist solely for old storage

Exit criteria:
- Public scene-graph semantics are expressed through BSG APIs only.


Validation Strategy
-------------------
For each phase:
- Build the smallest affected target set first.
- Re-run libbsg tests when BSG semantics or storage change.
- Re-run libdm/libged draw-path tests when renderer-facing behavior changes.
- Re-run Qt-enabled targets when view/qged/libqtcad selection or display paths
  are touched.

Recommended validation groups:
- Core:
  libbsg, libbv, libdm, libged
- UI/render:
  libqtcad, dm-qtgl, dm-swrast, qged, archer
- Draw tests:
  ged_test_bsg_view_obj
  ged_test_mged_bsg
  ged_test_mged_shaded_mode_bsg
  ged_test_tcl_adornment_bsg
  ged_test_qged_swrast

Special care areas:
- transparency pass behavior
- highlighted object color logic
- hidden-line mode
- adaptive mesh/BRep rendering
- selection/display-list invalidation
- backend cache invalidation/cleanup
- snap tolerance behavior tied to line width


Risk Management
---------------
High-risk changes:
- allocation/lifecycle ownership
- backend cache storage changes
- payload/vlist migration
- render-path removal of raw field assumptions
- removal of first-member casting between bsg_node and bv_scene_obj

Mitigations:
- keep compatibility shims until all major callers are migrated
- convert one semantic cluster at a time
- add regression tests before removing compatibility storage
- avoid simultaneous rewrites of payload, renderer, and lifecycle ownership


Suggested Execution Order
-------------------------
Recommended practical order:

1. Refresh inventory and decide permanent homes for remaining settings fields.
2. Remove all remaining raw s_os/s_local_os users in libbv/libdm/libged.
3. Move bsg_settings definition out of bv/defines.h using an intermediate
   compatibility header strategy if needed.
4. Replace embedded settings storage with BSG-owned or compat-sidecar storage.
5. Continue raw-field migration for identity, transform, payload, visibility,
   color/material, and backend cache.
6. Introduce BSG-native allocation/lifecycle ownership.
7. Shrink bv_scene_obj to compatibility-only status.
8. Remove first-member embedding/casting assumptions.
9. Delete transitional APIs and compatibility storage.


Recommended Immediate Next Steps
--------------------------------
1. Convert the remaining raw settings users:
   - src/libbv/snap.c
   - src/libbv/util.cpp
   - src/libbv/hash.c
   - src/libdm/dm-gl_lod.cpp
   - src/libdm/X/dm-X.c
   - src/libged/draw.cpp
   - src/libged/bsg_ged_draw.c

2. Decide the permanent home of mixed_modes.

3. Choose the storage transition mechanism:
   - shared transitional header
   - compat-sidecar storage
   - direct move to BSG-owned sidecars

4. After those are complete, move struct bsg_settings out of bv/defines.h.


Decision Point
--------------
If the project is willing to remove bv_scene_obj completely, that is the better
long-term direction.  In that case:

- do not optimize for preserving bv_scene_obj as a permanent storage type
- use compatibility shims only to ease the transition
- favor BSG-native ownership, allocation, and payload APIs even if they require
  more short-term changes

If the project wants a lower-risk intermediate landing first, stop after:
- removing raw settings users
- moving bsg_settings out of bv/defines.h
- storing legacy compatibility state outside the public bv_scene_obj layout

That gives a useful partial win without requiring immediate full elimination of
bv_scene_obj.
