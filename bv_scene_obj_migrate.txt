BV_SCENE_OBJ TO BSG FULL MIGRATION PLAN
======================================

Purpose
-------
Capture a complete migration plan for removing the remaining structural
dependency on struct bv_scene_obj as the effective scene-graph node backing
store, with particular focus on the remaining bsg_settings coupling and the
possibility of fully retiring bv_scene_obj in favor of first-class BSG types.


Current Situation Summary
-------------------------
1. bsg_settings is logically a BSG concept, but its struct definition still
   lives in include/bv/defines.h.

2. The immediate reason is storage and header layering:
   - struct bv_scene_obj embeds:
       struct bsg_settings *s_os;
       struct bsg_settings  s_local_os;
   - include/bsg/defines.h includes include/bv/defines.h.
   - include/bsg/settings.h includes include/bsg/defines.h.
   This means a simple move of struct bsg_settings into a libbsg header would
   create a circular dependency unless the storage or header layout changes.

3. The API migration is only partially blocked by callers.  Most high-level
   traversal code already uses typed BSG settings accessors, but some libbv,
   libdm, and libged code still touches bv_scene_obj settings storage directly.

4. The larger migration question is broader than settings.  bsg_settings is one
   example of a general problem: bsg_node is still physically embedded inside
   bv_scene_obj, and many subsystems still assume bv_scene_obj is the concrete
   node/container/payload object.


Primary Goal
------------
Arrive at a design where:

- BSG owns its node, material, appearance, payload, identity, and traversal
  contracts directly.
- bsg_settings either disappears entirely or becomes an internal transitional
  compatibility type that is no longer defined in bv/defines.h.
- libdm, libged, qged, mged, libqtcad, and libtclcad consume BSG APIs instead
  of raw bv_scene_obj fields.
- bv_scene_obj becomes either:
  A) a temporary compatibility wrapper with no unique semantic ownership, or
  B) removable entirely once the remaining raw-storage assumptions are gone.


Non-Goals
---------
- Do not attempt a big-bang rewrite.
- Do not break existing rendering behavior, edit workflows, or display-list
  lifecycles while refactoring ownership.
- Do not remove compatibility fields before equivalent BSG APIs exist and have
  been adopted by all non-test callers.


Key Constraints and Blockers
----------------------------
1. Header dependency cycle
   bsg/defines.h currently depends on bv/defines.h for struct bsg_node and the
   current compatibility layout.

2. Inline storage
   Embedded fields in bv_scene_obj require complete type definitions at header
   parse time, preventing simple forward-declaration-based decoupling.

3. Remaining raw field access
   The raw field inventory shows that many subsystems still touch bv_scene_obj
   fields directly beyond settings: names, paths, transforms, payloads, flags,
   color, backend cache, and custom data.

4. Transitional mixed ownership
   Some concepts already have BSG APIs but still write back into legacy
   bv_scene_obj fields for compatibility.

5. Unsettled semantic homes
   Not every bsg_settings field has a final destination yet:
   - draw_mode -> bsg_appearance
   - line_width -> bsg_appearance
   - arrow_tip_length / arrow_tip_width -> bsg_appearance
   - transparency -> material or appearance, depending on final policy
   - color_override / color -> bsg_material
   - draw_solid_lines_only / draw_non_subtract_only -> appearance or draw policy
   - mixed_modes -> still needs a clear permanent home


Migration Strategy Overview
---------------------------
Use a staged migration with two tracks:

Track 1: Remove the bsg_settings dependency on bv/defines.h.
Track 2: Remove bv_scene_obj as the concrete backing store assumption.

Track 1 can deliver incremental value even if Track 2 takes longer, but Track 2
is the cleanest long-term solution and should inform the API choices made in
Track 1.


Recommended End State
---------------------
Recommended target architecture:

1. struct bsg_node becomes the concrete first-class scene-graph node type.

2. Node-associated state is owned by BSG abstractions:
   - identity
   - material
   - appearance
   - payload
   - transform
   - selection/highlight state
   - renderer/backend compatibility hooks where still needed

3. bv_scene_obj becomes a compatibility layer only, then is retired.

4. bsg_settings is retired as a public structural dependency:
   - either replaced entirely by material + appearance + draw policy APIs, or
   - kept only as an internal compatibility snapshot outside bv/defines.h.

Phase 1 - Finish the Settings Semantic Split
--------------------------------------------
Objective:
Stop treating bsg_settings as the long-term semantic API.

Tasks:
- Define the permanent home of every bsg_settings field.
- Move callers away from thinking in terms of one monolithic settings blob.
- Decide where mixed_modes belongs:
  - bsg_appearance
  - a producer/draw request policy object
  - a renderer/draw command option

Recommended direction:
- Appearance:
  draw_mode, line_width, line_style/dash policy, inherit_settings,
  arrow_tip_length, arrow_tip_width, draw_solid_lines_only,
  draw_non_subtract_only
- Material:
  transparency, color override, explicit color source
- Producer/render policy:
  mixed_modes

Tasks by library:
- libdm: prefer bsg_appearance_get/material_get where possible instead of
  reading raw settings snapshots.
- libged: replace remaining settings-centric flows with appearance/material
  logic where no bundle copy is required.
- libbv: isolate any remaining bundle-copy/reset logic behind compatibility
  helpers rather than public structure ownership.

Exit criteria:
- No new code relies on bsg_settings as the canonical semantic type.

Phase 4 - Replace bv_scene_obj-Owned Settings Storage
----------------------------------------------------
Objective:
Make settings/appearance/material state BSG-owned rather than bv_scene_obj-owned.

Tasks:
- Remove the assumption that bv_scene_obj owns:
  - s_os
  - s_local_os
  - s_inherit_settings
- Store compatibility state in one of:
  - BSG node sidecar storage
  - appearance/material sidecars only
  - a dedicated compatibility extension object

- Eliminate s_local_os as embedded storage.
- Resolve inherit_settings through bsg_appearance.

Phase 8 - Final Cutover: Remove bv_scene_obj as the Backing Store

  helpers only in temporary compatibility code.

  bv_scene_obj facade for old API entry points.

Exit criteria:
- Non-compat production code no longer depends on struct bv_scene_obj.

- backend cache storage changes
- payload/vlist migration
